# Canwu Terminology / 参伍术语表

This document is the canonical Chinese-English terminology reference for
Canwu's public architecture, integration guides, tutorials, and agent-facing
documentation. It covers stable concepts that recur across those surfaces; it
does not attempt to translate every Rust identifier or temporary proposal term.

Use the Chinese term in Chinese prose and the English term in English prose.
Keep code identifiers exactly as written. On first use, write the Chinese term
followed by the English term or code identifier when that helps disambiguate it,
for example, **模拟插件** (`simulation plugin`) or **决策票据**
(`DecisionTicket`).

Linked terms already have a more detailed guide or architecture page. Unlinked
terms are currently defined only here and in their code-level API documentation.

Each concept has one preferred public term. The consolidated wording table below
marks alternatives as deprecated or restricted: deprecated terms must not be
introduced in new prose, while restricted terms remain valid only in the stated
technical context. Existing code identifiers and historical records are not
renamed by this policy.

| [插件输入撤回](../website/src/content/docs/developer/integration.mdx) | plugin ingress cancellation | `cancel_plugin_ingress`, `IngressPayload::PluginCancellation` | Terminal withdrawal of one still-queued plugin ingress item strictly before its due time, journaled as its own record. | [撤回权限](../website/src/content/docs/developer/integration.mdx) | cancellation authority | `IngressCancellationAuthority` | Who withdrew a queued plugin item: the host for public packets it enqueued, the owning plugin's registration permit for its internal packet type, or a boundary system of the plugin that scheduled the item. | [待处理输入](../website/src/content/docs/developer/persistence.mdx) | pending ingress | `pending_ingress`, `CanwuRun::pending_ingress` | Ingress records queued and not yet admitted or withdrawn, in the order boundaries will admit them, including records a seal or a continuation restore pinned. | [调度工作](../website/src/content/docs/architecture/events.mdx) | scheduled work | — | Work assigned a deterministic simulation due time and insertion order. |
| [结算边界](../website/src/content/docs/architecture/settlement.mdx) | boundary | `BoundaryRequest`, `BoundaryRecord` | One validated, all-or-nothing settlement pass that admits work, runs systems in fixed phases, records evidence, and commits or rolls back. |
| [结算阶段](../website/src/content/docs/architecture/settlement.mdx) | settlement phase | `BoundaryPhase` | One position in the fixed boundary execution order. A phase is ordering, not an independent settlement algorithm. |
| [原子提交](../website/src/content/docs/architecture/settlement.mdx) | atomic commit | — | Applying all validated changes from a boundary together so observers never see partial state. |
| [回滚](../website/src/content/docs/architecture/settlement.mdx) | rollback | — | Restoring state, evidence, counters, and random positions when a boundary fails. |
| [转移清单](../website/src/content/docs/architecture/settlement.mdx) | transition manifest | `TransitionManifest`, `BoundaryDirective::RegisterTransitionManifest` | A coordinating plugin's declaration of the participant plugins, expected record versions, and single ready boundary of one multi-owner transition. Participants stage their writes with `StageTransitionWrite` in phase 10 of that boundary; phase-10 directives outside a manifest are unaffected. |
| [转移审计](../website/src/content/docs/architecture/settlement.mdx) | transition audit | `TransitionAuditRecord` | The kernel's phase-11 check of every manifest ready at a boundary. A partially staged manifest or a wrong expected version fails the whole boundary; a manifest no participant staged expires. The committed or expired outcome is read-only boundary evidence for phase-12 systems. |
| [边界账](../website/src/content/docs/architecture/settlement.mdx) | boundary ledger | `SimulationView::boundaries_between`, `BoundaryWindow`, `BoundarySummary`, `BoundaryIngressOrigin`, `boundary_schedule_horizon` | The boundaries of a window of simulated time: those settled in it, the one being settled, and those still queued, each with its time, cadences, calendar marks, and ingress counted by class, kind, and origin. Only a phased boundary system may read it, after declaring `canwu.core.boundary_schedule`, to count a period's boundaries before it carries work into another one; it declares how far back it reads with `boundary_schedule_horizon`. Settled boundaries are the same in live, sealed, restored, and replayed runs; the queued list is a lower bound. |
| [历法标记](../website/src/content/docs/architecture/settlement.mdx) | calendar mark | `CalendarMark`, `schedule_calendar_marks`, `SimulationView::calendar_marks` | A host calendar's mark on a calendar boundary: the boundary is a period start (of a cadence) of that calendar. A system with a calendar key wakes only on its own calendar's marks of its cadence; a system without one wakes on every boundary of its cadence, marked or not. The core keeps no calendar. |
| [历法键](../website/src/content/docs/architecture/settlement.mdx) | calendar key | `BoundarySystemContract::calendar`, `MAX_CALENDAR_KEY_BYTES` | The host's name for one of its calendars (a canonical label of at most 64 bytes), on a mark and on a boundary system's registration, where it is part of the plugin descriptor. |
| [边界耗时明细](../website/src/content/docs/architecture/settlement.mdx) | boundary profile | `BoundaryProfile`, `set_boundary_profiling`, `take_boundary_profiles`, `replay_from_journal_with_boundary_profiles` | An opt-in host diagnostic: the wall time of one settled boundary, of each plugin handler it ran, by kind, phase, plugin, and name, and of each engine phase. It is never part of authoritative state, evidence, a snapshot, or replay, and no plugin can read it. An exact replay can be profiled boundary by boundary. |
| 引擎阶段 | engine phase | `BoundaryEnginePhase`, `BoundaryEngineTiming`, `BoundaryProfile::engine` | One kind of the simulation core's own work inside a boundary, timed in a boundary profile: admission, system dispatch, staging, commit, knowledge, journal, and hashing. The engine phases and the plugin handlers partition a boundary's wall time. It is a profiling category, not a settlement phase. |
| [请求结果保留期](../website/src/content/docs/developer/persistence.mdx) | request outcome retention | `RunConfiguration::request_outcome_retention`, `with_request_outcome_retention`, `DEFAULT_REQUEST_OUTCOME_RETENTION`, `MAX_REQUEST_OUTCOME_RETENTION` | How long, in simulated time after its attempt, a tracked command request's exact outcome and queued receipt are kept to answer an exact retry: 30 days by default, from zero to 366, fixed when the run is created. The rule is simulated time alone, so a wall-clock pause retires nothing, a fast simulation speed retires sooner in wall time, and unsealed, sealed, restored, and replayed runs answer alike. |
| [已退役请求结果](../website/src/content/docs/developer/persistence.mdx) | retired request outcome | `ErrorCode::RequestOutcomeRetired`, `RetiredRequestRange`, `RequestIndex::retired_commands` | What a tracked command request becomes once its attempt is older than the retention: its outcome is no longer kept, its ID stays used for the run inside a canonical range of retired IDs, and every later request with that ID, an exact retry or not, is refused with `RequestOutcomeRetired` without an attempt, a revision, or an event. A host that treats `IdempotencyConflict` as "take another ID" treats it the same way. Not 退休目标 (a culture target) and not 已清退条目 (a knowledge entry). |
