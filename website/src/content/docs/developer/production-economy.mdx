参伍 0.13.0 提供可选的资源与生产扩展，但不会把粮食、工厂、价格、历史资源点或军队写进模拟内核。

## 推荐边界

- 模拟内核负责命令准入、确定性时间、阶段顺序、原子提交、回滚、可见性、存档与重放。
- `canwu-resource` 负责资源/单位版本、`ResourceAccount`、受保护底线、`ResourceDemand`、`ResourceReservation`、精确分配腿、转移、消费、损耗和履约，是物理余额的唯一写入者。
- `canwu-production` 负责工艺、生产地点、设施、产能、工单、在制品、执行、项目和产出结算；它消费精确资源结果与技术证据，但不保存另一套库存。
- `canwu-transport` 负责行程、容量、路线腿、执行、保管权交接和交付完成记录；自 0.13.0 起，由 `canwu-movement` 负责移动执行及其运力池的生命周期。资源扩展负责货物托管余额、损耗、接受、退回与目的地入账。
- 人口和军事领域分别形成需求与后果，不能直接改写资源余额或生产状态。

这些可选扩展都建立在公开 `canwu-api` 之上，不会反向进入模拟内核。上层游戏仍负责货币、市场、工资、建筑界面、战斗公式和历史内容。

## 先理解三个术语

| 术语 | 含义 |
| --- | --- |
| 受保护底线 | 账户必须保留、不能发布给本次资源分配的最低数量 |
| 资源预留 | 绑定精确需求、账户、资源/单位版本和生命周期的 `ResourceReservation`；失败或回滚不能留下隐藏占用 |
| 托管前驱 | 允许下一次货物状态转换的上一条精确记录，用于防止重复入账或凭空增加货物 |

## 一个最小循环

```text
需求 -> 资源预留/分配 -> 来源账户扣减 -> 在途托管 -> 到货验收
     -> 目的地入账 -> 下一结算边界允许消费
```

1. 运行中的需求通过持有人授权的资源命令提交和修改。类型化适配器输入仅支持已声明的提供方操作，不支持需求提交或修改；消费者不能直接写库存。
2. `canwu-resource` 按受保护底线、最低有效量、部分履约政策、到期时间和稳定 tie-break 生成确定性分配腿。
3. 生产、军事或其他消费者引用精确分配与履约证据，只写本领域的工单或后果记录。
4. 只要守恒、版本、托管前驱或权限校验失败，整组提案回滚。
5. 目的地只有在货物处置被接受后才入账；军事消费在下一次合适的结算边界生效。

库存余额是唯一可写数量。预留量、可用量和储备视图都必须从它派生；“到达”不是“可消费”，路线可达也不是交付。

## 授权自定义消费者

自 0.10.1 起，参伍支持自定义消费提供方使用现有 `ResourceConsumptionIntentV1` 合同。
在插件拥有的有效领域记录中保存顶层 `resource_consumption_intents` 映射，
每个键等于对应已封存意图的 `id`。无需回调，也无需冒用参考提供方名称。
在 `ResourcePlugin::new` 中注册该记录种类，使适配器能够读取精确来源。

提交前，先完成现有的分配与完成租约生命周期。通过规范适配器输入提交
`ResourceOperationRequestV1::Consume`。其中 `consumer_evidence` 必须等于
提供方的精确**当前**来源；完成凭证必须绑定该来源和同一操作键。
持有者、参与者、时间、版本及租约校验仍然适用。

必须恰有一个 `Authorized` 意图匹配完整分配腿、需求与账户版本、消费标识
和操作键。该合同不支持只消费分配腿的一部分。映射条目数不得超过资源状态的
`max_operation_outcomes`；超限会在解码前被拒绝。缺失或格式错误的映射、
标识或摘要不符，以及已退役、有歧义或不匹配的授权都会被拒绝。
封存摘要只验证内容一致性，本身不授予权限。拒绝不会授权扣减。

提供方负责意图的授权、退役以及资源回执产生后的本领域后果；
`canwu-resource` 负责守恒余额和重复操作的处理。军事补给参考消费者保留其
专用适配器及不同的保留来源政策；自定义消费者应使用上述当前来源合同。

## 版本与存档

应用必须精确固定同一发布线的 `canwu-api`、`canwu-resource`、`canwu-production` 与插件语义哈希。加载时恢复同一参伍快照并重新验证扩展记录；不能把旧快照只按“当前时间”重建，也不能把未发布的本地引擎版本当成兼容 API。

## 需求来源策略

自 0.11.0 起，每个 `ResourceDemand` 都持久化保存 `source_policy`：

- `ResourceDemandSourcePolicyV1::Pooled` 保留原有资源池行为，按账户 ID 的确定性顺序，从资源版本和单位版本均匹配的所有开放账户分配。
- `ExactAccounts(Vec<ResourceAccountId>)` 明确列出 1–256 个账户；ID 必须严格递增且不重复。每个账户必须存在、未关闭、与需求的资源和单位版本精确匹配，且保管人为需求申请者。无效列表在资源变化前产生命令拒绝；分配时会再次验证。
- 自 0.13.0 起，`Granted { grant_id, accounts }` 以同样方式列出 1–256 个账户，但每个账户都必须由所指动用授权的授权方保管，且该授权的被授权方必须是申请者（见[动用授权](#动用授权)）。

分配器仅以所选账户计算可用量、最低有用量和部分履约。明确列出的账户不足时，不会回退到资源池。受保护底线，以及后续转移和消费的权限检查仍然适用。精确来源路径只访问列表中的账户，数量受 `MAX_DEMAND_SOURCE_ACCOUNTS` 限制；资源池路径保留原有账户扫描。

首次分配前，可携带预期版本修改需求来源策略。一旦存在任何资源预留（包括已消费、但仍对应在途转移托管余额的预留）或任何履约，策略便不可再改。需要新策略时，应取消需求并提交新需求；取消需求不会取消独立的转移。预留历史会保留在索引中，直到需求终止、相关归档记录具备归档条件；终止需求不能修改。自 0.13.0 起，修改也不能改变需求的生命周期状态、拒绝原因或申请者；这样的修改会被记录为拒绝，而不再造成此后的边界无法推进。

`Pooled` 是选择策略，不是动用其他保管人库存的授权。上层应用必须控制谁可以提交资源池需求，以及使用哪个申请者；`ExactAccounts` 列表同样不能证明任何委托。带上限和有效期的跨保管人委托只能通过动用授权与 `Granted` 策略表达；任命、用途以及谁可以授权给谁，仍由应用或领域规则负责。转移保管权限和完成租约仍需单独验证。

策略进入请求摘要、运行时快照、精确重放和终止需求归档载荷。恢复时验证有效来源引用与保留预留的账户归属；归档验证保留策略及其摘要。持有人相对报告沿用现有可见性合同，不会自动公开权威来源列表。独立 DTO 缺少 `source_policy` 时反序列化为 `Pooled`，但这不迁移旧快照：引擎版本和插件身份的精确检查仍然适用。Rust 结构体字面量必须补充该字段，因此这是 0.11.0 的源码不兼容变更。

## 账户损耗

自 0.12.0 起，`ResourceOperationRequestV1::RecordLoss(ResourceAccountLossRequestV1)` 可以直接在单个账户上记录腐坏、失窃或其他损耗，而不必虚构一次转移。请求携带自己的 `loss_id`、精确账户版本、数量、原因和完成凭证，结算为 `account: Some(..)`、`transfer: None` 的 `ResourceLoss`，并在守恒总量中计为已准入损耗。

扣减不会动用已预留存量；除非设置 `allow_protected`，否则遵守受保护底线；账户版本过期会被拒绝。带请求标识的命令必须来自账户保管人；规范适配器输入可以把原因记录作为提供方来源引用。持有人报告会包含 `ResourceLossObservationV1` 条目，其可见性与转移详情相同。

## 原子交换

`ResourceOperationRequestV1::BeginExchange(ResourceExchangeStartRequestV1)` 同时发起两条转移腿：两项转移要么都创建，要么都不创建；无论成功还是被拒绝，唯一的 `BeginExchange` 结果都会在 `cited_transfers` 中列出两个转移 ID。

1. 双方先约定 `ResourceExchangeTermsV1`：交换键，以及每条腿的转移 ID、精确分配和目的地。
2. `ResourceExchangeTermsV1::leg_operation_keys` 从这些条款的摘要派生每条腿的操作键。
3. 每条腿的来源保管人为该腿的派生键取得完成租约，因此每份租约都表示同意整个交换，不能用于其他条款。
4. 由 `leg_a` 的来源保管人把交换作为带请求标识的命令提交。

交换本身没有单独的完成凭证。发起之后，两项转移各自独立结算，因此可能一项被验收、另一项损耗或退回。原子交换不是委托访问：每一方仍只能动用自己保管的存量。

## 本地验收

`ResourceTransferDispositionV1::AcceptLocal { destination, expected_destination_revision, handover_evidence }` 不经运输执行即可结算一项转移，例如同一仓库或同一城镇内的交接。它只适用于仍处于 `PendingDispatch`、没有运输关联的转移，并且两个账户必须声明相同的 `ResourceAccount::place_scope`。

地点范围由场景在安装账户时声明，不可更改，引擎也不会推断；默认值为 `None`，带请求标识的 `CreateAccount` 命令不能设置它。缺少或不一致的地点范围会以 `invalid_definition` 拒绝，已关联运输的转移会以 `invalid_lifecycle` 拒绝。终止凭证会锁定精确的交接记录；带请求标识的命令必须来自目的地保管人。

## 实际产出

`ProductionOperation::CompleteExecution` 可以携带 `realized_output_per_mille` 和 `realization_evidence`。该比例以工艺名义产出的千分比表示，`None` 表示 1,000。第 7 阶段按该比例对每项产出结算数量向下取整缩放，并把两个值保存在生产执行上；资源入账和产出确认随后精确结算缩放后的数量。

- 任何非 1,000 的比例都需要精确证据记录版本，其种类必须列在工艺版本的 `realization_evidence_kinds` 中；名义比例若附带证据会被拒绝。该列表默认为空，因此默认工艺只接受名义产出。
- 比例必须为正数，也不能把任何产出腿缩放为零。完全损失应通过取消工单记录。
- 比例不能超过工艺版本的 `max_realized_per_mille`，默认值为 1,000；更高的上限允许有证据支持的超名义产出。
- 持有人、生命周期、比例和种类规则会先于证据记录解析运行，因此拒绝结果不会泄露其他记录是否存在。

## 动用授权

自 0.13.0 起，一个保管人可以让另一方直接动用自己的存量，而不必先转移存量。动用授权（`ResourceAccessGrantV1`）记录授权保管人、被授权方、精确的资源与单位版本、上限 `cap_quantity`、半开区间有效期 `valid_from..valid_until`，以及证明该授权的精确 `authority_evidence` 记录版本，例如应用中已被接受的征发记录。

1. 授权保管人以受跟踪命令提交 `ResourceOperationRequestV1::IssueAccessGrant`；权限证据必须是可用的精确记录版本。适配器输入不能签发或撤销授权。
2. 被授权方提交来源策略为 `ResourceDemandSourcePolicyV1::Granted { grant_id, accounts }` 的需求。授权必须有效且被授权方就是申请者，资源与单位必须匹配，需求的时间窗口必须位于授权有效期内，列出的每个账户都必须开放并由授权方保管，数量也不能超过剩余上限。
3. 分配在稀缺资源仲裁之前检查授权。已撤销或不在有效期内的授权不提供任何供给，任何分配都不会超过剩余上限，也不会回退到资源池或其他账户。
4. 被授权方在自己的完成租约下扣减分配结果，方式可以是消费，也可以是发起转移或交换的一条腿。动用授权下的扣减只能在时间等于其认证时间的边界结算，且该时间必须位于授权有效期内，因此在有效期内认证、却在有效期后才结算的扣减会被拒绝。其他任何人（包括授权方）持有的租约都不能扣减动用授权下的分配。

`ResourceAccessGrantRecordV1` 保持 `cap_quantity = remaining + reserved + debited`：分配把数量移到 reserved，扣减再移到 debited，因此每个单位只计扣一次；释放或过期的预留会回到 remaining。由动用授权下的分配发起的转移会记录其 `access_grant`，其取消、退回和损耗由被授权方而不是来源保管人控制；本地验收仍属于目的地保管人。`RevokeAccessGrant` 同样由授权方凭预期授权修订号提交，一旦有任何预留或扣减就会被拒绝，因此应按委托的实际需要设定上限和有效期。动用授权需求中过期的预留，会在为被授权方运行的下一次分配中释放；上层应用通过 `enqueue_resource_allocation` 发起这次分配。

授权保存在热状态中，受 `MAX_RESOURCE_ACCESS_GRANTS`（4,096）限制，且不归档，因此应像控制账户创建一样控制谁可以签发授权。`resource_access_grant_status` 是绑定持有人的读取接口，供授权方或被授权方查看授权及其计数。谁可以授权给谁、授权背后的记录，仍属于应用的权限。

例如，应用中的征发 saga 先记录人口所有者的同意；所有者再引用这条同意记录签发授权，军队随后提交 `Granted` 需求，并用自己的租约扣减分配结果。

## 实时生产产出结算

0.13.0 之前，通过实时命令完成的生产执行无法结算产出。执行完成租约中的资源一方，在授予租约时就把生产运行时记录锁定在当时的版本上，而那时执行尚不存在；之后每次生产转移都会推进这条记录。现在，产出记账引用协调器在执行上固定为 `output_source` 的精确生产版本。资源运行时接受该版本作为锁定记录（不早于锁定版本），生产产出批次输入也要求它与固定的来源完全一致；通用资源适配器输入会拒绝生产记账。因此，在开始时间或之后通过实时命令完成执行，现在都会结算产出。
