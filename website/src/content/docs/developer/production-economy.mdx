参伍 0.10.1 提供可选的资源与生产扩展，但不会把粮食、工厂、价格、历史资源点或军队写进模拟内核。

## 推荐边界

- 模拟内核负责命令准入、确定性时间、阶段顺序、原子提交、回滚、可见性、存档与重放。
- `canwu-resource` 负责资源/单位版本、`ResourceAccount`、受保护底线、`ResourceDemand`、`ResourceReservation`、精确分配腿、转移、消费、损耗和履约，是物理余额的唯一写入者。
- `canwu-production` 负责工艺、生产地点、设施、产能、工单、在制品、执行、项目和产出结算；它消费精确资源结果与技术证据，但不保存另一套库存。
- `canwu-transport` 负责行程、容量、路线腿、执行、保管权交接和交付完成；资源扩展负责货物托管余额、损耗、接受、退回与目的地入账。
- 人口和军事领域分别形成需求与后果，不能直接改写资源余额或生产状态。

这些可选扩展都建立在公开 `canwu-api` 之上，不会反向进入模拟内核。上层游戏仍负责货币、市场、工资、建筑界面、战斗公式和历史内容。

## 先理解三个术语

| 术语 | 含义 |
| --- | --- |
| 受保护底线 | 账户必须保留、不能发布给本次资源分配的最低数量 |
| 资源预留 | 绑定精确需求、账户、资源/单位版本和生命周期的 `ResourceReservation`；失败或回滚不能留下隐藏占用 |
| 托管前驱 | 允许下一次货物状态转换的上一条精确记录，用于防止重复入账或凭空增加货物 |

## 一个最小循环

```text
需求 -> 资源预留/分配 -> 来源账户扣减 -> 在途托管 -> 到货验收
     -> 目的地入账 -> 下一结算边界允许消费
```

1. 需求通过资源命令或类型化适配器输入提交，消费者不能直接写库存。
2. `canwu-resource` 按受保护底线、最低有效量、部分履约政策、到期时间和稳定 tie-break 生成确定性分配腿。
3. 生产、军事或其他消费者引用精确分配与履约证据，只写本领域的工单或后果记录。
4. 只要守恒、版本、托管前驱或权限校验失败，整组提案回滚。
5. 目的地只有在货物处置被接受后才入账；军事消费在下一次合适的结算边界生效。

库存余额是唯一可写数量。预留量、可用量和储备视图都必须从它派生；“到达”不是“可消费”，路线可达也不是交付。

## 授权自定义消费者

0.10.1 支持自定义消费提供方使用现有 `ResourceConsumptionIntentV1` 合同。
在插件拥有的有效领域记录中保存顶层 `resource_consumption_intents` 映射，
每个键等于对应已封存意图的 `id`。无需回调，也无需冒用参考提供方名称。
在 `ResourcePlugin::new` 中注册该记录种类，使适配器能够读取精确来源。

提交前，先完成现有的分配与完成租约生命周期。通过规范适配器输入提交
`ResourceOperationRequestV1::Consume`。其中 `consumer_evidence` 必须等于
提供方的精确**当前**来源；完成凭证必须绑定该来源和同一操作键。
持有者、参与者、时间、版本及租约校验仍然适用。

必须恰有一个 `Authorized` 意图匹配完整分配腿、需求与账户版本、消费标识
和操作键。该合同不支持只消费分配腿的一部分。映射条目数不得超过资源状态的
`max_operation_outcomes`；超限会在解码前被拒绝。缺失或格式错误的映射、
标识或摘要不符，以及已退役、有歧义或不匹配的授权都会被拒绝。
封存摘要只验证内容一致性，本身不授予权限。拒绝不会授权扣减。

提供方负责意图的授权、退役以及资源回执产生后的本领域后果；
`canwu-resource` 负责守恒余额和重复操作的处理。军事补给参考消费者保留其
专用适配器及不同的保留来源政策；自定义消费者应使用上述当前来源合同。

## 版本与存档

应用必须精确固定同一发布线的 `canwu-api`、`canwu-resource`、`canwu-production` 与插件语义哈希。加载时恢复同一参伍快照并重新验证扩展记录；不能把旧快照只按“当前时间”重建，也不能把未发布的本地引擎版本当成兼容 API。
