参伍的模拟内核保持领域中立。上层应用通过模拟插件、领域 schema、命令处理器和边界系统
添加军事、经济、政治或社会规则，而不是修改实时世界对象。

## 选择扩展方式

| 需求 | 使用 |
| --- | --- |
| 一个用户动作或服务请求产生局部变化 | 用 `register_command()` 注册领域命令 |
| 多个系统在同一日结、回合或时间点协调 | 用 `register_boundary_system()` 注册边界系统 |
| 插件拥有类型化领域数据 | 注册领域 schema，并通过领域记录 API 读写 |
| 结果需要稳定随机性 | 声明插件随机流，让每次抽样进入证据记录 |

## 最小模拟插件结构（节选）

下面的代码只展示注册结构；载荷 schema、处理器和完整导入见可运行示例。

```rust
struct StancePlugin;

impl SimulationPlugin for StancePlugin {
    fn name(&self) -> &'static str { "example-stance" }
    fn version(&self) -> &'static str { "1.0.0" }
    fn semantic_hash(&self) -> &'static str { "a33fb7c59ae5a17685bd94f99154c5423dc7bf70d3dbde6ef4daf73670a37d26" }

    fn register(&self, registrar: &mut PluginRegistrar<'_>) -> Result<(), CanwuError> {
        registrar.register_command(stance_descriptor(), set_stance)
    }
}
```

`stance_descriptor()` 声明载荷结构与读写 `StateKey`；`set_stance()` 通过只读
`SimulationView` 查询军队，使用 `CommandContext` 检查发令者，并返回
`SystemDirective` 描述变化。它不取得可变世界引用。

运行完整示例：

```shell
cargo run -p canwu-api --example plugin
```

合法指挥官提交 `set_stance` 后，参伍验证载荷与权限并提交姿态组件；未经授权的发令者会得到
`InvalidAuthority`，且状态不会发生部分修改。

## 何时使用边界系统

当供给、需求、资源分配和后果必须在同一个结算边界协调时，使用边界系统。合同应声明：

- 结算阶段与运行频率；
- 读取、写入和同边界可见性；
- 资源供给、预留请求和分配依赖；
- 可能发出的领域事件；
- 所需随机流和领域 schema。

参伍按固定阶段运行系统、验证声明式访问、完成确定性分配，并原子提交结果。
完整例子见[阶段边界与资源分配](/tutorials/phased-boundary/)。

## 从需求到可重放扩展

1. 为插件选择稳定名称、版本和语义哈希。
2. 注册插件拥有的领域 schema、命令和边界系统。
3. 让处理器只读取 `SimulationView`，并返回声明式变化。
4. 通过公开入口提交领域命令或规范化输入，不保留实时运行时引用。
5. 验证保存、加载、精确重放、权限失败和原子回滚。

仍由内容包或上层应用拥有。

## 生命周期规则

- 在依赖插件的命令、场景验证或加载发生前注册插件。
- 从存档恢复或重放时提供相同的插件集合与语义哈希。
- 不要让插件持有实时运行时引用或绕过规范化输入修改状态。
- 把语义哈希变化视为可执行行为变化，并配套迁移或新版本。
- 应用代码只通过 `canwu-api` 使用扩展合同。

在实现前，先阅读[架构中的五条边界](/architecture/#五条架构边界)，再从最接近需求的公开示例开始。
