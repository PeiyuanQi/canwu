## 先确定恢复目标

| 目标 | 保存 | 加载 | 上层应用要做的事 |
| --- | --- | --- | --- |
| 普通存档或服务重启 | `snapshot_json()` | `Canwu::from_snapshot_json_with_plugins()` | 保存完整快照，加载时提供相同的插件集合 |
| 长期运行的紧凑存储 | `checkpoint_journal_json()` | `Canwu::from_checkpoint_journal_json_with_plugins()` | 保存检查点及其后连续不断的日志 |
| 只保存变化部分的增量存档 | `prepare_paged_checkpoint()` | `Canwu::from_paged_checkpoint_and_journal_with_plugins()` | 保留每个状态页和连续不断的证据前缀，见[分页检查点](#分页检查点) |
| 审计或精确重建 | `replay_journal()` | `Canwu::replay_from_journal()` 或 `replay_from_journal_json()` | 保存完整日志，并保留匹配的插件集合 |
| 向外部系统发送效果 | `outbox_entries()` | — | 至少投递一次，按 `delivery_id` 去重，并保存确认状态 |
| 从同一时点尝试另一组输入 | `fork()` | — | 把派生分支当作新的平行现实 |

## 保存与恢复快照（节选）

```rust
use canwu_api::Canwu;
use canwu_reference_world::{ReferenceWorldPlugin, demo_scenario};

let (scenario, _) = demo_scenario()?;
let plugin = ReferenceWorldPlugin;
let canwu = Canwu::new_with_plugins(35, scenario, &[&plugin])?;

let json = canwu.snapshot_json()?;
let restored = Canwu::from_snapshot_json_with_plugins(&json, &[&plugin])?;
assert_eq!(restored.checkpoint_hash(), canwu.checkpoint_hash());
```

加载时会验证快照的格式、引擎版本和插件描述，任何一项不符都会失败。存档中一旦有插件领域记录，加载时就要传入同样的插件。

[`starter` 示例](https://github.com/PeiyuanQi/canwu/blob/main/crates/integrations/canwu-reference-world/examples/starter.rs)把这段流程与派生分支、精确重放放在一起运行：

```shell
cargo run -p canwu-reference-world --example starter
```

## 检查点日志与精确重放

**检查点日志**（`CheckpointJournal`）把一个经过验证的检查点，与其后连续不断的证据打包在一起。它从检查点出发，只携带之后记录的证据，适合长期运行。

**精确重放**根据日志中的初始场景、输入和已记录证据，重建同一次模拟运行：

```rust
let checkpoint_journal = canwu.checkpoint_journal_json()?;
let from_checkpoint =
    Canwu::from_checkpoint_journal_json_with_plugins(&checkpoint_journal, &[&plugin])?;
assert_eq!(from_checkpoint.checkpoint_hash(), canwu.checkpoint_hash());

let journal = canwu.replay_journal();
let replayed = Canwu::replay_from_journal(&[&plugin], &journal)?;
assert_eq!(replayed.checkpoint_hash(), canwu.checkpoint_hash());
```

精确重放的规则：

- 场景取自日志；`replay_from_journal()` 只接收插件集合和日志。
- 运行身份、引擎版本、插件语义环境和已记录证据都必须匹配。
- 重放直接使用已记录的结果：决策、随机抽样和外部答复都从日志读取，副作用也不会再发送一次。

## 平行现实

`fork()` 把当前时点的模拟复制成一个独立的模拟，适合比较另一组命令、策略或研究假设。派生分支照常通过命令和时间接口推进；输入一旦不同，它就是新的平行现实，与原运行的精确重放是两回事。

## 向外部发送效果：外发队列

需要送达外部系统的边界输出会出现在 `outbox_entries()` 中。每个 `OutboxEntry` 都有稳定的 `delivery_id`，由运行、结算边界、事件和输出序号派生而来。

1. 在自己的存储中保存每个 `delivery_id`，以及对应的投递状态和确认状态。
2. 按“至少一次”投递，超时或重启后可以安全重试。
3. 接收方按 `delivery_id` 去重，因为同一次网络调用可能发生不止一次。
4. 精确重放会生成相同的 `delivery_id`，投递仍由上层应用负责。

在紧凑模式（`CompactedCanwu`）下，`seal_evidence()` 返回封存后的 `EvidenceJournalSegment`。请把这个日志段与投递、确认状态一起保存。封存或压缩证据，并不表示效果已经投递或确认。

## 高级存储与归档

只有当快照体积或热历史增长真正成为问题时，才需要分页检查点、`StatePageProvider`、决策历史归档和插件归档参与者。到那时，上层应用必须：

- 按内容标识保存每个状态页，并原样返回相同字节；缺页必须报错，不能当作空数据；
- 保留每个检查点所需的连续日志前缀和归档保留根；
- 保留资源归档的查找页：恢复、精确重放或派生分支沿途经过的每个归档头都需要它们（见[归档终态记录](/architecture/resources-production/#归档终态记录)）；
- 为每个插件恢复相同的归档契约和语义哈希；
- 删除冷数据前，先从已提交的根做可达性检查。

### 分页检查点

**分页检查点**是当前状态检查点按内容寻址的形式：它以状态页的形式保存在 `StatePageProvider` 中，之后每个新检查点只增加发生变化的页。从 0.13.2 起，可以通过对外 API 写出和恢复分页检查点：

- **写出。** `Canwu::prepare_paged_checkpoint(source, provider)` 把当前状态整理成一个 `PreparedPagedSimulationCheckpoint`。其中的增量不包含提供方已经持有的页；`source` 是上一个检查点（如果有）。`store_and_verify` 负责保存这份增量。准备检查点不会改动模拟运行：状态修订号、检查点哈希和所有日志都保持不变。
- **恢复。** `Canwu::from_paged_checkpoint_and_journal(checkpoint, provider, segments)` 和 `from_paged_checkpoint_and_journal_with_plugins` 根据提供方和证据前缀重建模拟运行。证据前缀是从运行开始到该检查点为止、连续不断的日志段，可以在运行过程中用 `journal_segment_since` 逐段收集。每个日志段至少要包含一条新记录，所以起点与终点相同的日志段要跳过。恢复时执行的验证与加载快照相同。提供方只需持有恢复时实际读取的页；读取的页缺失时会以 `StatePageUnavailable` 失败，不会当作空数据。对已归档的决策历史，恢复只读取热决策状态所依赖的页；其他已归档历史会报告 `Unresolved`，直到通过提供相同页的 `DecisionArchiveProvider` 调用 `decision_history_location_with_provider` 查到它。
- **紧凑模式。** `CompactedCanwu` 提供同样的调用。它的证据前缀是你已封存的日志段（按封存先后排列），再加上用 `journal_segment_since` 从最后一段的终点取得的日志段；如果封存之后没有记录任何内容，就跳过这最后一段。紧凑模式恢复之后，证据前缀会改变，见[重启紧凑模式的模拟运行](#重启紧凑模式的模拟运行)。

检查点本身不携带证据记录。除了紧凑模式的接续信息（例如每次封存对应的一个归档日志段头），它的大小取决于当前状态，而不是运行持续了多久；每份增量只包含发生变化的页。准备检查点时仍可能读取保留的证据，恢复时也仍会验证完整的证据前缀。

需要注意：

- 提供方要一直保留之前检查点的页。从分页检查点恢复的模拟运行再准备检查点时，增量同样不包含它从未加载过的已归档决策页，所以它的提供方必须已经持有恢复所用检查点的全部页。`store_and_verify` 只检查新增的页和根；要检查一个检查点的完整页集合，请使用 `StatePageRetentionLedger::prepare` 和 `verify`。
- 检查点列有插件时，紧凑模式的恢复必须使用 `_with_plugins` 形式。
- 分页根不是状态标识，因为它还绑定了哪些证据已经封存。凡是从已封存日志段恢复，无论通过 `Canwu` 还是 `CompactedCanwu`，检查点哈希都与原运行相同，分页根却不同，之后再封存也不会变回原来的分页根。从未封存过证据的运行，恢复后的分页根与原来相同。判断状态是否相同，请比较检查点哈希，而不是分页根。

### 重启紧凑模式的模拟运行

紧凑模式的恢复，无论是从分页检查点恢复，还是通过 `CompactedCanwu::from_checkpoint_and_journal` 及其 `_with_plugins` 形式恢复，都会把你传入的整个证据前缀作为保留证据。这会改变之后恢复所需的日志段：

1. 恢复后的模拟运行再次封存之前，它的检查点使用你恢复时传入的证据前缀，再加上用 `journal_segment_since` 从该前缀终点取得的日志段。
2. 它下一次调用 `seal_evidence()` 时，会返回一个从运行开始处起算的日志段，取代之前封存的所有日志段。
3. 从此以后，证据前缀以这个新日志段开头，再加上用 `journal_segment_since` 从它的终点取得的日志段。
4. 之前的日志段只需为那次封存之前的检查点保留。

如果证据前缀仍把之前的日志段放在新日志段前面，前缀就不连续，恢复会失败。

格式编号、分页存储契约和归档不变量见仓库中的[版本与持久化契约](https://github.com/PeiyuanQi/canwu/blob/main/docs/versioning.md)。

## 版本与存档兼容

:::note
参伍 0.15.0 写出快照格式 8、承诺格式 4、检查点/证据日志格式 4 和分页检查点封装格式 4。存档还记录了精确的 `engine_version`，所以 0.15.0 引擎只能加载 0.15.0 写出的存档。0.14.0 及更早版本的存档不能加载，改写其中记录的版本号也不行；需要读取时，请保留旧引擎，或用自己的工具导出数据。
:::

参伍 0.15.0 是次版本。各种格式和哈希算法都没有变化，引擎也没有往存档里多写任何东西：回答[操作定址随机抽样](/architecture/randomness/#抽样之后还有哪些开销)的索引在恢复时重建，[边界耗时剖面](/architecture/settlement/#边界耗时剖面)从不保存。与存档和代码有关的变化如下：

- **修正了一种写出后无法加载的存档。** 知识记录可以[取代或标为矛盾](/architecture/knowledge-information/#取代先前的记录)哪些记录，加载存档时现在使用与结算相同的规则。在 0.14.0 中，如果插件在同一时刻的两个边界里先后取代某位持有人的记录，写出的存档就无法加载。
- **封存过的模拟运行与重放的行为一致。** 完全相同的[操作定址随机抽样](/architecture/randomness/#封存证据之后的重试)重试，即使它引用的证据已被 `seal_evidence` 移走，也能拿回已记录的抽样；0.14.0 会以 `InvalidRandomOperationEvidence` 拒绝。封存之后发布的[财政报告](/architecture/fiscal/#报告如何发布)会取代封存之前发布的那一份；在 0.14.0 中，持有人会同时留着两份当前报告，封存过的模拟运行也无法通过精确重放。
- **需要修改的代码。** `PersonDraft` 用可选的 `PersonPlacement` 取代了 `government` 和 `current_location` 两个字段，`BoundaryPersonCreation::person` 的类型变为 `BoundaryCreatedPerson`。`SocietyPlugin` 不再是单元结构体，请写 `SocietyPlugin::DAILY`。`ResourceState::prepare_resource_archive` 多了一个归档存储参数。`ResourceCompletionOperationV1` 和 `FiscalAction` 新增了变体。`SocietyCohortExchangeLedger`、`ResourceArchiveIndexDirectoryV1`、`PreparedResourceArchiveBatchV1`、`ResourceProtectedFloorRequestV1`、`FiscalAuthorityBinding`、`FiscalAuditFinding` 和 `FiscalState` 新增了公开字段，所以底线请求的结构体字面量要加上 `install: None`，权限绑定的字面量要加上 `rebound_by: None`。`MAX_RESOURCE_ARCHIVE_LOOKUP_DIRECTORIES` 已移除。读取财政报告请用 `fiscal_reports`；单独一条 `fiscal_report` 记录不再能解码成完整的 `FiscalProjection`。
- **插件身份。** society 插件、资源插件和财政插件的语义哈希改变。使用 society 的模拟运行，只能用注册了相同[结算节奏](/tutorials/cases/local-community-diffusion/#换一种结算节奏)的插件恢复和重放。
- **资源归档。** 请保留资源归档的查找页：恢复、精确重放或派生分支会读取沿途每个归档头的查找索引，见[归档终态记录](/architecture/resources-production/#归档终态记录)。0.14.0 写出的归档目录无法解码，不过 0.15.0 的模拟运行不可能读到它们。
- **财政记录在进入时校验。** 无效的财政目录或状态，在创建或恢复模拟运行时就会被拒绝；在 0.14.0 中，要到第一个准入了内容的边界才失败。财政状态记录现在引用每个观察者指向的人物，所以请用 `FiscalState::into_record` 构造它；写到了不存在的观察者的状态会被拒绝。`fiscal_report` 知识 schema 升到版本 2，场景的知识里如果带有版本 1 的报告记录，也会被拒绝。
- **拒绝不再卡住模拟运行。** 被拒绝的 society 命令和有缺陷的 society 输入现在记录为拒绝；候选预算已满时，失效的资源归档提交也不再让之后的每个边界失败。带请求标识的资源命令如果用已有的操作键提交内容不同的请求，会被拒绝或不予结算。同一个边界可以结算多个财政行动，连结果都记不下的行动会被丢弃并留下一个事件。

和任何一次版本变化一样，每个检查点哈希中的引擎版本都会改变。从 crate 版本取得插件版本的第一方插件，也会报告新的插件版本。精确的引擎版本检查会拒绝 0.14.0 的存档；需要读取时，请保留 0.14.0 引擎。

上一个次版本参伍 0.14.0 把 0.13.3 按天读取边界的方式，换成了可以读取[任意一段模拟时间](/architecture/settlement/#统计一段时间内的边界)的方式：`SimulationView::boundaries_between(from, to)` 返回 `BoundaryWindow`，供上层应用调用的是 `Canwu::boundaries_between` 和 `CompactedCanwu::boundaries_between`。边界系统用新的契约字段 `BoundarySystemContract::boundary_schedule_horizon` 声明要往回读多远（最长 `MAX_BOUNDARY_SCHEDULE_HORIZON`，即 366 天）。`boundaries_on_day` 和 `DayBoundaries` 已移除，所以用到它们的代码，以及用结构体字面量构造 `BoundarySystemContract` 的代码，都需要修改。这个字段为零时不会写入保存的契约，所以其他插件的描述和语义哈希不变，各种格式和哈希算法也不变。和任何一次版本变化一样，每个检查点哈希中的引擎版本都会改变。从 crate 版本取得插件版本的第一方插件，也会报告新的插件版本。精确的引擎版本检查会拒绝 0.13.3 的存档；需要读取时，请保留 0.13.3 引擎。

此前的补丁版本参伍 0.13.3 首次加入了这项读取，当时按天读取：边界系统声明新的 `StateKey::core_boundary_schedule` 读取后可调用的 `SimulationView::boundaries_on_day`，供上层应用调用的 `Canwu::boundaries_on_day` 和 `CompactedCanwu::boundaries_on_day`，类型 `DayBoundaries`、`BoundarySummary`、`BoundaryIngressCount`、`BoundaryIngressKind` 和 `BoundaryIngressOrigin`，以及 `SimTime::day` 和 `SimTime::MINUTES_PER_DAY`。恢复时，引擎根据日志重建当天已结算的边界，所以存档没有新增字段。所有改动都是新增，现有代码无需修改即可编译，各种格式、公开类型的结构和哈希算法都没有变化。和任何一次版本变化一样，每个检查点哈希中的引擎版本都会改变。从 crate 版本取得插件版本的第一方插件，也会报告新的插件版本。精确的引擎版本检查会拒绝 0.13.2 的存档；需要读取时，请保留 0.13.2 引擎。

参伍 0.13.2 是补丁版本。引擎内部早已实现[分页检查点](#分页检查点)的写出和恢复，这个版本把相关调用加入对外 API：`Canwu::prepare_paged_checkpoint`、`Canwu::from_paged_checkpoint_and_journal` 和 `Canwu::from_paged_checkpoint_and_journal_with_plugins`，`CompactedCanwu` 上同样的三个调用，以及 `CompactedCanwu::journal_segment_since`。所有改动都是新增，现有代码无需修改即可编译。各种格式、公开类型的结构和哈希算法都没有变化。每个检查点哈希都包含引擎版本，所以和任何一次版本变化一样，每次运行的检查点哈希，以及记录这些哈希的分页根，都与 0.13.1 不同。从 crate 版本取得插件版本的第一方插件，也会报告新的插件版本。精确的引擎版本检查会拒绝 0.13.1 的存档；需要读取时，请保留 0.13.1 引擎。

上一个补丁版本参伍 0.13.1 的格式和现有公开类型与 0.13.0 相同，另新增三个公开项：`SimulationView::replay_stable_domain_record_version`、`canwu_military::MILITARY_REJECTION_EVENT` 和 `OperationState::validate`。它的检查点哈希都与 0.13.0 不同，0.13.0 的存档也不能加载。生产、历史研究、财政、军事和资源插件的语义哈希也发生了变化，`canwu-economy-reference` 插件及其类型化证据适配器、`canwu-force-supply-reference` 插件同样如此。

它修复了一个问题：在一直运行、未经存档恢复的模拟中，[推迟的决策票据](/architecture/decisions/)过了截止时间也不会到期，之后针对它的请求却都以 `ClosedTicket` 被拒绝。现在这类票据会在截止时间之后的第一个结算边界到期，与从快照恢复的模拟一致。

它还修复了证据检查的一个问题：同一条命令在用 `seal_evidence` 封存过的模拟运行中可能被拒绝，在该运行的精确重放中却被接受。现在[生产](/developer/production-economy/)执行、设施项目和实际产出、[动用授权](/developer/production-economy/#动用授权)、财政折纳报价和[财政执行凭证](/architecture/fiscal/)，以及历史研究评估列出的精确记录版本，都必须是封存无法改变的版本，通常就是每条记录的当前版本。历史研究评估中事件、边界等通用引用仍按保留的证据检查，所以封存过的模拟运行仍可能拒绝其精确重放会接受的评估。此外，有问题的[军事](/architecture/military/)和财政命令不再让之后的每个结算边界都失败，而是记为被拒绝。

- 需要保存存档的应用，请固定到确切的发布版本或 Git 修订。
- 插件语义哈希变化意味着行为变化。任何版本发布，即使是补丁版本（例如 0.13.0 → 0.13.1），都可能同时改变多个扩展的语义哈希，使用这些扩展的旧存档随之无法加载。
- 参伍不迁移旧存档。要跨引擎版本保留历史，请运行自己的导出与导入流程，或保留写出这些数据的旧引擎。
- 新版本会增加枚举变体和结构体字段，穷举 `match` 和结构体字面量可能需要随之修改。

各版本的具体变化见[版本与持久化契约](https://github.com/PeiyuanQi/canwu/blob/main/docs/versioning.md)。

## 上线前检查

- 固定引擎版本和插件语义环境。
- 完整走一遍：保存、重启进程、加载，再比较检查点哈希。
- 做一次精确重放，比较最终检查点哈希。
- 模拟一次外发超时，确认按 `delivery_id` 重试不会重复产生外部效果。
- 写明版本升级时旧存档如何处理：导出后重新导入、保留旧引擎读取，还是放弃。
