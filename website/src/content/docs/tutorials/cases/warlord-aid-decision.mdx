## 1. 要解决什么问题

假设你正在制作一个军阀混战时期的历史模拟。军阀甲正在交战，请求相邻的
军阀乙派兵支援。最初，军阀乙只知道共同敌人确实存在，却还不能确认补给路线
是否安全；新情报到达后，“派兵支援”才成为一个可执行选项。

你需要的不只是让 AI 返回“同意”或“拒绝”，而是一条可以进入正式游戏循环的
决策链：

- 情报变化后，安全地更新当前可选方案；
- 无论决策者是 AI、玩家还是外部模型，都只能选择已有选项，不能凭空生成命令；
- 选中“派兵支援”后，由获授权的控制者（controller）提交经过验证的命令；
- 保存每次尝试、评分和执行结果，使存档恢复与精确重放不必再次询问决策者。

这是一个带北洋时期风格的合成案例，不是对具体人物、机构或有记录事件的复原。人物性格、情报来源和“为什么值得援助”等历史语义
仍由你的领域包定义；参伍负责守住决策、权限、命令和证据之间的边界。

## 2. 我们如何实现

这个案例把多个系统串在一起：

| 系统 | 在案例中的作用 | 相关文档 |
| --- | --- | --- |
| 决策票据、控制者与决策策略 | 保存问题、当前选项、决策身份和评分过程 | 本页下文 |
| 权限与命令入口 | 把选中的决策选项转成经过验证的命令 | [架构总览](/architecture/)、[接入并驱动模拟运行](/developer/integration/) |
| 结算边界 | 准入决策输入，持久化决策轨迹，再执行派生命令 | [结算系统](/architecture/settlement/) |
| 角色相对信息 | 用军阀乙可见的事实构造决策上下文（context），避免泄露全知状态 | [安全读取与呈现状态](/developer/reading-state/) |
| 存档与精确重放 | 保存票据、决策尝试、决策轨迹和命令证据 | [存档、重放与派生分支](/developer/persistence/) |

先运行示例：

```shell
cargo run -p canwu-api --example decision_ticket
```

程序会输出一条完整的 `DecisionTrace`。`WeightedUtilityPolicy` 最终选择
`send-aid`，决策轨迹会记录每个选项的总分和逐项贡献；示例随后恢复存档并执行
精确重放，验证两条路径得到完全相同的快照。

### 实现流程

```text
军阀乙可见的事实
  -> 打开 DecisionTicket
  -> 新情报到达，ReplaceOptions
  -> 效用策略只选择已有 option ID
  -> 控制者派生签发者与权限
  -> 普通 Command 验证和执行
  -> 持久化 DecisionTrace
```

<Steps>
1. 注册 `warlord-b-ai` 控制者，把它绑定到明确的决策策略身份、负责人物和可控制军队。
2. 打开援军请求票据。补给路线尚未确认，因此最初只有“拒绝援助”可选。
3. 路线确认后，通过 `DecisionMutation::ReplaceOptions` 更新决策上下文，并加入 `send-aid`。
4. 使用 `WeightedUtilityPolicy` 为当前选项计算确定性整数分数。
5. 调用 `drive_decision()` 生成决策结算输入；下一个规范边界持久化决策轨迹，并把选中的命令交给普通命令入口。
6. 保存快照、重新加载并执行精确重放，确认重放不需要再次运行决策策略。
</Steps>

### 第一步：绑定决策身份与行动权限

```rust
let controller = DecisionControllerBinding::new(
    "warlord-b-ai",
    DecisionPolicyIdentity::new(
        DecisionPolicyKind::Utility,
        "aid-utility",
        "1",
    ),
    DecisionAuthority::Actor { actor: ids.commander },
)
.with_command_subject(EntityRef::Army(ids.army));
```

控制者不是领域 AI 的“大脑”。它只持久化三件事：由谁作决定、使用哪个
决策策略，以及选中选项后可以代表谁控制什么。决策策略不会获得签发者、席位、
permission profile，也拿不到可变世界引用。

### 第二步：用票据保存一个明确问题

`DecisionTicketDraft` 保存稳定定义、决策者、控制者、截止时间、显式
决策上下文和当前选项。示例开始时只提供 `decline`：

```rust
DecisionMutation::Open {
    ticket: DecisionTicketDraft {
        id: DecisionTicketId::new(1),
        definition: "beiyang.request-military-aid".to_owned(),
        decision_maker: EntityRef::Person(ids.commander),
        assigned_controller: "warlord-b-ai".to_owned(),
        summary: "Neighboring warlord requests immediate military aid".to_owned(),
        context: DecisionContext::new(
            "beiyang.aid-request.v1",
            json!({ "common_enemy": true }),
        ),
        options: vec![DecisionOption::new("decline", "Decline aid")],
        deadline: Some(now + SimDuration::days(2)),
    },
}
```

正式应用应从军阀乙的角色知识或观察结果构造决策上下文，而不是把
全知的世界状态直接交给决策策略。

### 第三步：让新情报显式改变选项

本案例中的路线确认由上层应用作为场景观察提供，并未绑定史料证据。研究应用应先关联证据记录，再把它称为权威事实。随后应用提交一次由 `expected_version` 保护的选项
替换：

```rust
DecisionMutation::ReplaceOptions {
    ticket_id: DecisionTicketId::new(1),
    expected_version: 1,
    context: DecisionContext::new(
        "beiyang.aid-request.v1",
        json!({ "common_enemy": true, "route_confirmed": true }),
    ),
    options: vec![decline, send_aid],
}
```

更新后，票据版本会递增。Human、External 或 LLM 决策策略如果仍提交旧版本
答案，就会被拒绝，不会误选已经变化的选项集合。

`send-aid` 可以保存一个序列化的既有参伍命令，但决策策略只能返回它的
option ID。下面可运行的 `canwu-api` 示例是刻意保留的兼容性夹具；它用旧版
`Command::OrderMovement` 验证通用决策框架：

```rust
DecisionOption::new("send-aid", "Send the neighboring army").with_command(
    serde_json::to_value(Command::OrderMovement {
        subject: EntityRef::Army(ids.army),
        destination: ids.eastern_territory,
        cargo: Vec::new(),
    })?,
)
```

新应用应通过 `canwu-reference-world` 编码 `MovementCommand`，或在自己的领域
crate 中定义等价的插件命令。当前接入方式见[移动军队](/tutorials/move-army/)；
决策票据可以保存任一形式，因为它持久化的是在控制者权限下选中的
序列化命令。

### 第四步：用效用评分解释为什么出兵

```rust
let policy = WeightedUtilityPolicy::new(
    "aid-utility",
    "1",
    UtilityProfile {
        weights: BTreeMap::from([
            ("alliance".to_owned(), 3),
            ("home_defense".to_owned(), 1),
        ]),
    },
);
```

每个选项提供由领域定义的整数输入。通用评估器计算 `value * weight`，
使用稳定 option ID 处理平分，并把逐项贡献写入决策轨迹。引擎不理解“同盟信誉”或
“本土防御”的历史含义；这些含义和权重属于领域或决策策略。

### 第五步：让决策策略选择，让控制者行动

```rust
canwu.drive_decision(
    canwu.time(),
    0,
    DecisionRequestId::new(4),
    Some(CommandRequestId::new(1)),
    DecisionTicketId::new(1),
    &policy,
)?;
canwu.step_canonical()?;
```

这里始终保留两道边界：

- 决策策略只能选择票据中已有且未被阻止的选项。
- 控制者从持久化绑定派生命令权限；命令仍要通过参伍的
  普通权限、修订版本、时间和领域验证。

所以，即使把效用策略换成玩家、外部服务或 LLM，也不会获得任意生成命令
或伪造军阀乙权限的能力。

### 第六步：保存决策轨迹，并在重放时复用证据

`decision_attempts()` 返回每次规范准入的接受或拒绝结果。旧的修订版本、
旧票据版本或已经关闭的票据会形成持久化拒绝，而不是让同一条输入持续回滚并
卡住模拟。`decision_traces()` 则返回成功结算的选择结果、票据版本、决策策略
身份、效用分项、外部证据和命令请求 ID。

快照会保存控制者、票据、当前选项、截止时间、决策尝试与决策轨迹。
精确重放消费已经记录的决策输入、决策尝试和命令尝试，不会再次询问玩家、
外部服务或模型。如果你要比较另一套决策策略，应从快照派生分支（`fork`）后
产生新的决策输入；那是平行现实，不是精确重放。

可替换的决策方式包括：

- `WeightedUtilityPolicy`：用确定性评分表达战略 AI、人物性格或军事条令参数；
- `OrderedRulePolicy`：按规则顺序选择或推迟；
- `GuardedUtilityPolicy`：前置规则效用策略，先由有序前置规则选择、推迟或排除选项，再做效用评分，并可在分数接近的最高选项之间随机平局决胜；
- `QueuedHumanPolicy`：等待 UI 或玩家提交绑定票据版本的选择；
- `QueuedExternalPolicy`：通过集成适配器调用外部决策服务；
- `QueuedLlmPolicy`：把决策上下文和选项描述交给模型，但不暴露命令动作。

自 0.12.0 起，决策轨迹会记录决策阶段（`Guard`、`Utility` 或 `Random`）以及触发的
前置规则。票据还可以用 `parent_ticket` 指定前序票据：新票据所接续的、同一决策者的
终态票据。

如果军阀乙死亡或被俘，参伍会在该边界结束时取消以军阀乙为决策者的未关闭票据；在军阀乙
仍不可用期间，也会拒绝为其开启新票据。如果只是控制者的权限人物（即控制者代其行事的
人物）不可用，参伍会取消该控制者的未关闭票据，并拒绝再为它开启新票据。要继续这类决策，
请为可用的控制者开启新票据，并把 `parent_ticket` 设为已取消的票据；这一关联会复制到
新的决策轨迹上。
