> **当前合同。** 路由和运输类型最早在 0.5 引入，并仍属于当前 0.13.0 对外 API。集成方仍需提供网络与历史内容数据。自 0.13.0 起，`canwu-movement` 扩展负责其所准入运输执行的生命周期并分配运力池；地图导入、通用历史数据集和把运输记录提升为模拟内核快照字段仍是后续工作。

如需直接运行把这些机制接入定向信息投递的完整流程，请看
[从无锡出发的经路线规划通信](/tutorials/cases/routed-correspondence/)。该案例使用
`canwu-correspondence` 模拟领域扩展；本页继续解释更底层的规划与执行契约。

## 先分清两个问题

“从无锡去北京怎么走？”至少包含两层：

1. **规划**：在当前观察者知道的网络、时刻表、风险和容量事实下，哪条路线能在约束内最早到达？
2. **执行**：这封信是否已经装载、出发、到达中转站、交接、遇灾改道，并最终完成对应收件人的送达尝试？

`canwu-routing` 只负责第一层；`canwu-transport` 记录第二层。它们不会绕过 `canwu-sim` 的规范化输入（canonical ingress），也不会直接修改 `canwu-information` 的收件人账本。

## 无锡到北京

规划输入必须带观察者和知识切口，而不是直接读取全知世界：

```rust
let request = RoutingRequest {
    origin: RoutingNodeRef::new("settlement/wuxi"),
    destination: RoutingNodeRef::new("settlement/beijing"),
    departure_at: SimTime::from_hours(8),
    policy: RoutingPolicy {
        allowed_modes: [TransferMode::Rail, TransferMode::Horse]
            .into_iter()
            .collect(),
        ..RoutingPolicy::default()
    },
};

let plan = plan_route(&planning_snapshot, &request)?;
```

`PlanningSnapshot` 可以来自当前世界的路线适配器，也可以由铁路、空运、电报或古代驿站扩展自己提供。它绑定 `observer`、`knowledge_cut`、拓扑版本和有效期，所以一个知道铁路时刻表的人，和一个只知道驿站传闻的人，可以得到不同的合法计划。
如需只用某个持有人知道的内容构建快照，可使用 `canwu-correspondence` 的 `planning_snapshot_from_holder_knowledge`，见[按持有人知识规划路线](/developer/reading-state/#按持有人知识规划路线)。

如果近邻收件人的投递点位于同一地区，路由可能只需要一条短途步行或马匹 leg；去北京则可能需要多个驿站、车站和交接。路由器不会因为目标是“另一个人”就把两者当成同一个终点。

## ETA 不是送信期限

`RoutePlan.estimated_arrival_at` 是执行估计；`DeliveryAttempt.due_at` 是信息生命周期中的逻辑完成期限。预计晚到不能偷偷改写原始期限：系统应记录失败；若要再次投递，应创建新的后继 `DeliveryAttempt`。

同样，改道和投递重试不是一回事：

- **改道**：创建新的不可变 `ItineraryRevision`，仍属于同一个投递尝试；
- **投递重试**：创建新的后继 `DeliveryAttempt`，可以选择新的路线和运输方式。

## 铁路、空运、电报与驿站

历史差异放在网络数据中，而不是复制四套寻路算法：

- 铁路使用 `TransferMode::Rail`、车站节点、发车 slots 和容量 booking；1900 年与 1940 年只需要不同的内容包和时刻表。
- 空运使用 `TransferMode::Air`、机场、班次、天气可用性和容量 booking。
- 电报或其他信号使用 `TransferMode::Signal`，把电报局开放时间、延迟、风险和截获规则作为数据或扩展政策。
- 古代驿站使用中继站节点、马匹或步行路段，以及明确的保管权交接 `Handoff`。

固定时长、发车时刻和分段时长分别由 `Fixed`、`Departures` 与 `Piecewise` traversal 表达。非 FIFO 的时变网络必须显式选择有预算的 label-correcting 算法；默认 FIFO 网络使用确定性 Dijkstra。

## 执行与遇灾

拿到计划后，上层应用把它安装到运输执行记录，并通过信息尝试的版本建立完成桥：

```rust
let mut execution = TransportExecution::new(
    TransportExecutionId(7),
    Some(delivery_attempt_version.clone()),
);
execution.install_initial_itinerary(initial_revision)?;
execution.begin_saga(
    delivery_attempt_version,
    delivery_completion_operation_key(
        TransportExecutionId(7),
        ItineraryRevisionId(1),
        1,
    ),
)?;
```

每一 leg 有自己的状态和实际出发/到达时间。到达中转站后，先记录 `Handoff`，再开始下一 leg。遇到洪水、战乱、天气或线路中断时，领域系统记录明确的失败原因，执行进入 `ReplanPending`，然后基于新的 `PlanningSnapshot` 安装后继行程修订；新修订还会记录从失败路段到新首段的保管权交接。到达前后不适用的事故会保留为 suppressed 证据，不会改写信息状态或到达等待状态。路由器不会自行“猜”灾害。

最后一 leg 到达后，执行进入 `ArrivalPending`。`completion_request()` 产生稳定的 operation key 和证据，上层应用通过规范化输入（canonical ingress）调用信息扩展完成送达；重复提交同一 key 不应重复完成。

## 人员群体、扣押与外部条件

自 0.12.0（`canwu-transport.v4`）起，运输记录新增三项常用表达：

- `MovementSubjectRole::PersonsGroup` 表示人员群体：把一群人作为一个移动主体，其身份通常是应用领域记录。与货物一样，它必须带正数数量，这里表示人数；`requires_quantity()` 给出这条规则。
- `HandoffKind::Seizure { by }` 记录扣押交接：行程之外的主体夺取保管权，例如盗匪或敌方驻军。它与计划交接遵循相同的路段规则。自 `canwu-transport.v5` 起，扣押也可以是终态的：它以当前修订中一个失败的路段同时作为起止路段，保管权随之离开行程。每个执行只允许一次终态扣押；此后该执行不能再使路段失败或改道、到达、结算、预订运力或记录其他交接，只能由其所有者以失败或取消关闭。普通交接仍是计划交接（`Planned`），序列化结果与以前相同。
- `ItineraryRevisionReason::ExternalCondition { record, version, kind }` 以外部条件说明改道：引用应用所有的条件记录（例如洪水或封关记录）的精确版本及应用标签；初始行程和每次改道都会校验它。

运输只记录这些事实。是否发生扣押或灾害、由谁授权，仍由应用系统决定。

## 移动生命周期与运力池

`canwu-transport` 仍是记录库。自 0.13.0 起，移动生命周期扩展 `canwu-movement` 负责这些记录的生命周期，上层应用不必再逐段手动推进。注册 `MovementPlugin::new(evidence_kinds)` 时，列出它可以读取的应用记录种类，例如权限记录、投递尝试、外部条件记录和事故证据；这份列表就是它的精确读取集合。

- **移动命令。** 受跟踪命令 `apply_movement_operation_v1` 携带来自签发者自身持有人的 `MovementCommandV1`。`Order` 操作准入一条 `MovementOrder` 并创建其运输执行；发起操作的持有人成为所有者，可选的操作者和延迟的远方观察者获得报告授权。若要移动所有者以外的对象，需要权限依据 `authority_basis`：一条已声明种类的应用记录的当前版本，它以 `movement_grantee` 角色指明所有者，并以 `movement_subject` 角色指明其他每个对象。
- **路段。** 每个路段通过内部 `movement_leg_due_v1` 输入在到期时结算；`StartLeg`、`CompleteLeg`、`FailLeg`、`Reroute`、`RecordHandoff` 和 `Cancel` 则是显式操作。最后一段到达时运输执行随之结算；若附有投递尝试，则进入 `ArrivalPending`。
- **事故。** 应用系统通过公开的 `movement_incident_v1` 输入报告失败、改道、扣押交接和投递核对，并引用已声明种类的精确证据记录。插件从不抽样；危险是否发生，由你的系统抽样决定。
- **运力池。** `OfferPool` 操作提供运力池（`TransportCapacityPoolV1`）：在时间窗口内可以互换的一定数量运力，例如渡船班次或驿马。`RequestBooking` 为一个尚未出发的路段、在其计划窗口内申请运力。第 7 阶段对每个运力池运行一次预订分配：本边界申请的每项预订要么全额确认，要么记录证据后失败，顺序依次为优先级、窗口开始时间、平局决胜键、准入序号和预订标识；已确认的运力不会被抢占。出发的路段消耗其预订；预订失败或过期的路段以 `capacity_unavailable` 失败并等待改道；已确认但窗口尚未开始的预订会推迟出发。
- **报告。** 插件向存活的人物持有人发布 `canwu.movement/movement_report` 知识：所有者和操作者看到当前执行情况，延迟的远方观察者只看到一个延迟时长之前的粗略进度，没有授权的持有人什么也看不到。

每个操作键只有一个持久结果，因此完全相同的重试不会产生新效果。已关闭的运输执行会在最终报告发出后、且最迟在关闭 365 天后从运行时移除；已发布的报告和记录历史保留发生过的事情。分配函数 `allocate_capacity_bookings` 也是公开的纯函数，自行管理生命周期的上层应用可以沿用同样的排序。限额与错误码见该 crate 的 [README](https://github.com/PeiyuanQi/canwu/blob/main/crates/extensions/canwu-movement/README.md)。

## 容量与确定性

车次、航班、驿站马匹和电报线路都可以用 `CapacityBooking` 表示。booking 是持久的窗口记录，状态变化包括请求、确认、消耗、释放、过期、取消和失败；自 `canwu-transport.v5` 起，预订可以在窗口开始前确认、失败或取消，但只能在窗口内消耗。路线缓存不能隐藏容量写入。移动执行可以使用上文的运力池，但当前通信契约仍只暴露 `CorrespondenceCapacityAdmission::Unconstrained`，不能启动受容量约束的路段。未来的准入变体必须携带应用或基础设施适配器提供的精确 booking 或模拟资源预留证据。

`RoutingCache` 只由规划快照摘要、请求和策略派生，丢失后可重建，不进入快照或精确重放。搜索扩展数、转运次数、风险和到达时间上限也属于策略的一部分，因此“无路可走”和“超过预算”都是可重放的确定性结果。

想了解所有权边界和 M1–M3 checklist，请阅读[架构页](/architecture/)与[仓库中的 routing/transport proposal](https://github.com/PeiyuanQi/canwu/blob/main/docs/proposals/routing-transport-mechanism.md)。
