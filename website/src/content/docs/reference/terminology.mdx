本页用于查询参伍术语：中英文名称、对应的代码标识及含义。带链接的术语另有专门页面详细说明，其余术语以本页和 API 文档中的定义为准。

编写参伍文档时，请在中英文中分别使用表中的规范写法，代码标识保持原样，并避免使用最后一张表中标为已弃用的写法。首次出现时可以同时给出英文或代码名，例如**模拟插件**（simulation plugin）或**决策票据**（`DecisionTicket`）。仓库中的 [`docs/terminology.md`](https://github.com/PeiyuanQi/canwu/blob/main/docs/terminology.md) 是术语的权威来源，本页与之同步。

| [准入](/architecture/events/) | admission | — | 决定哪些待处理输入进入某个边界的过程和切点；它不是 ingress 的同义词。 |
| [插件输入撤回](/developer/integration/) | plugin ingress cancellation | `cancel_plugin_ingress`, `IngressPayload::PluginCancellation` | 在到期之前终止撤回一项仍在排队的插件输入，并作为独立日志记录保存；被撤回的输入永远不会被准入，也不会发生回滚。 |
| [撤回权限](/developer/integration/) | cancellation authority | `IngressCancellationAuthority` | 撤回排队插件输入的主体：上层应用撤回自己提交的公开数据包，所属插件以注册许可撤回其内部数据包类型，或由安排该输入的插件的边界系统撤回。只有签发者可以撤回。 |
| [调度工作](/architecture/events/) | scheduled work | — | 具有确定模拟到期时间和插入顺序的工作。 |
| [结算边界](/architecture/settlement/) | boundary | `BoundaryRequest`, `BoundaryRecord` | 一次经过验证、要么全部提交要么整体回滚的结算：准入工作，按固定阶段运行系统，记录证据。 |
| [结算阶段](/architecture/settlement/) | settlement phase | `BoundaryPhase` | 固定边界执行顺序中的一个位置，不代表一套独立结算算法。 |
| [原子提交](/architecture/settlement/) | atomic commit | — | 一次性应用边界中所有通过验证的变化，避免暴露部分状态。 |
| [回滚](/architecture/settlement/) | rollback | — | 边界失败时同时恢复状态、证据、计数器和随机位置。 |
| [转移清单](/architecture/settlement/) | transition manifest | `TransitionManifest`, `BoundaryDirective::RegisterTransitionManifest` | 协调插件为一次多所有者转移作出的声明，列出参与插件、预期记录版本和唯一的就绪边界。参与者在该边界第 10 阶段用 `StageTransitionWrite` 暂存写入；清单之外的第 10 阶段指令不受影响。 |
| [转移审计](/architecture/settlement/) | transition audit | `TransitionAuditRecord` | 内核在第 11 阶段对本边界就绪的每份清单所做的检查。清单仅被部分参与者暂存，或预期版本不符，都会使整个边界失败；没有任何参与者暂存的清单则过期。提交或过期的结果作为只读边界证据，供第 12 阶段系统读取。 |
| [边界账](/architecture/settlement/#统计一段时间内的边界) | boundary ledger | `SimulationView::boundaries_between`、`BoundaryWindow`、`BoundarySummary`、`BoundaryIngressOrigin`、`boundary_schedule_horizon` | 一段模拟时间内的边界：其中已经结算的、正在结算的和仍在排队的边界，每个都带有时间、节奏，以及按类别、种类和来源计数的输入。只有分阶段的边界系统可以在声明 `canwu.core.boundary_schedule` 读取后读它，在把工作带到另一个边界之前先数清这段时间的边界；它用 `boundary_schedule_horizon` 声明要往回读多远。已结算的边界在实时、封存、恢复和重放的运行中完全相同；排队列表只是下限。 |
| [边界耗时明细](/architecture/settlement/#边界耗时明细) | boundary profile | `BoundaryProfile`、`set_boundary_profiling`、`take_boundary_profiles`、`replay_from_journal_with_boundary_profiles` | 上层应用按需开启的诊断数据：一个已结算边界的现实耗时，它运行的每个插件处理器的现实耗时（按种类、阶段、插件和名称列出），以及每个引擎阶段的耗时。它不属于权威状态、证据、快照或重放，插件也读不到它。精确重放可以逐个边界计时。 |
| [引擎阶段](/architecture/settlement/#边界耗时明细) | engine phase | `BoundaryEnginePhase`、`BoundaryEngineTiming`、`BoundaryProfile::engine` | 边界耗时明细中模拟内核自身工作的一个类别：准入、系统调度、暂存、提交、知识、日志和哈希。引擎阶段与插件处理器一起分完一个边界的现实耗时。它是计时类别，不是结算阶段。 |

| [法律制度化](/architecture/culture-law/) | legal institutionalization | `canwu-law` | 位于文化等社会证据下游的实验性扩展：推进法律程序，经控制者决策记录待处理法律意图，并在插件边界内原子写入法律渊源、规则和不可变版本；文化不能直接写入法律状态。 |
| [法律渊源版本](/architecture/culture-law/) | legal source version | `LegalSourceVersion` | 不可变的法律渊源记录，可表示制定文书、判决、协议、习惯认可结论、法律承受表或其他由内容配置的法律主张依据。 |
| [法律规则](/architecture/culture-law/) | legal rule | `LegalRule` | 一项有界规范规则的稳定身份与可变 head；其不可变变更保存在 `LawVersion` 记录中。 |
| [法律版本](/architecture/culture-law/) | law version | `LawVersion` | 绑定稳定 `LegalRule` 的仅创建、不可变规范变更记录，保存确切渊源与前序引用、规范关系、适用范围、生效与效力状态以及证据；执行情况另行建模。 |
| [法律记录引用](/architecture/culture-law/) | legal record reference | `LegalRecordRef` | 分片法律运行时中法律对象的精确 kind 与身份；法律插件拥有自己的对象/版本语义，并分别持久化 plan、directory、shard 与 archive-head 记录，因此它不是内核 `DomainRecordVersionRef`。 |
| [文化目标代际引用](/architecture/culture-law/) | cultural target generation reference | `CulturalTargetGenerationRef` | 法律提案或版本引用的精确目标与 generation，防止退休或重新激活把旧证据静默绑定到新一代。 |
| [文化执行计划](/architecture/culture-law/) | compiled culture plan | `CompiledCulturePlan` | 从文化定义编译出的外部不可变、绑定内容哈希的运行时计划，包含紧凑 ID、反向索引、预算和生命周期策略。 |
| [休眠目标](/architecture/culture-law/) | dormant target | `Dormant` | 没有参与人口或已准入工作的文化目标；它离开热结算索引，但保留显式重新激活描述。 |
| [退休目标](/architecture/culture-law/) | retired target | `Retired` | 从动态热状态移除的文化目标；历史身份和证据仍通过墓碑与归档契约保留。 |
| [文化结算插件](/architecture/culture-law/) | culture boundary plugin | `CultureBoundaryPlugin` | 在引擎内完成文化结算的插件形式：每月第 7 阶段系统消费已准入的接触信号批次，保存文化状态，并把 society 生命周期变化交给 society 插件；society 插件仍是唯一写入者。一次运行只能在它与由上层应用驱动的 `CulturePlugin` 流程之间二选一。 |
| [接触信号批次](/architecture/culture-law/) | exposure signal batch | `CultureExposureSignalBatch`, `culture_exposure_v1` | 信息或通信提供方在解决访问与解释之后产生的有界、带证据的报告，说明哪些 cohort 接触了某一文化目标代际；它在之后的边界准入。 |
| [cohort 人口校准](/tutorials/cases/local-community-diffusion/) | cohort headcount rebase | `CohortHeadcountRebaseV1`, `cohort_headcount_rebase_v1` | 把 cohort 人口重置为所引用外部存量记录的规范化输入；输入准入时，该记录必须是当前版本。下一次 society 结算会按确定性的整数最大余数法，按比例重算每个分布。 |
| [society 结算节奏](/tutorials/cases/local-community-diffusion/#换一种结算节奏) | society settlement cadence | `SocietyPlugin::with_settlement_cadence`, `SocietyPlugin::DAILY` | 决定 society 在哪些边界结算的 `SystemCadence` 类别：默认是 `Daily`，也可以由上层应用指定。转化速率每次结算生效一次，society 写入系统要应用的一切变化都等到带这个节奏的边界。节奏记录在插件描述中，所以恢复和重放必须使用同一节奏的插件。 |
| [转移结算模式](/tutorials/cases/local-community-diffusion/#换一种结算节奏) | transfer settlement | `TransferSettlement`、`SocietyPlugin::with_transfer_settlement` | society 结算如何检查到期的 cohort 转移。**批量结算**（`Batch`，默认）把每笔到期转移都按结算开始时的状态检查，仍然成立的按准入顺序逐笔应用，每笔都在前面几笔留下的状态上执行；数量已经放不下的转移结算为 `insufficient_source`。**逐笔结算**（`OneByOne`）把每笔转移按同一次结算中更早的转移留下的状态检查，所以涉及同一个 cohort 的到期转移只有一笔完成，其余结算为 `stale_source`。模式是插件身份的一部分。 |
| 社群输入队列 | society ingress queue | `SocietyIngressQueue`、`SocietyIngressBatch`、`society_ingress_queue_entries` | 等待下一次 society 结算的人口校准、生命周期变化和压力修订所在的队列：一条很小的头记录，加上每个准入了输入的边界各一条批次记录，所以它的证据只随各边界准入的数量增长。队列已满时到达的输入以记录在案的 `queue_full` 结果被拒绝。 |

| [征询阶段](/architecture/culture-law/) | consultation stage | `ProcedureStageKind::Consultation` | 仅供咨询的程序阶段。其席位收到标注为 advisory 的票据，选票作为参与证据保存，但从不计入结果；阶段在截止时间完成，并开启下一阶段。 |
