Canwu 不把随机数当作一个全局、不可追踪的黑盒。随机性属于带命名、版本和所有者的流；每次抽样都会留下足够的证据，让相同运行环境可以重新得到相同结果。

## 随机流身份

一个 `RandomStreamKey` 由 `namespace`、`name` 和 `version` 组成，例如：

```text
canwu.core / knowledge-report-delay / 1
```

内核从运行根种子和流身份派生独立种子。不同领域使用不同流，因此报告延迟的抽样不会因为另一个系统增加了一次抽样而改变。流状态保存算法、初始种子、当前位置和生成器状态。

当前算法标记为 `SplitMix64V1`。算法名称和版本属于持久化契约；将来更换算法应使用新的版本，而不是悄悄改变旧流的含义。

## 声明后才能抽样

阶段系统只能使用自己在 `BoundarySystemContract.random_streams` 中声明并拥有的流。建立随机会话时，内核复制允许流的状态；未声明的流会被拒绝。

每次范围抽样都要求：

- 上界大于零；
- `purpose` 非空且已经规范化；
- 流位置可以安全递增。

插件只得到一个有界整数，不直接接触全局生成器状态。

## 抽样证据

每次抽样都会记录：

| 字段 | 含义 |
| --- | --- |
| 流与位置 | 哪一条版本化流的第几次抽样 |
| 上界与结果 | 请求的范围和实际值 |
| purpose | 这次抽样在领域中的语义用途 |
| producer | 边界系统或内核系统 |
| outcome | 例如边界决策或报告送达 |
| cause / correlation | 因果来源和处理链关联 |

抽样记录和流状态一起进入快照、边界证据和哈希。发生失败回滚时，流位置和抽样记录也一起恢复，避免“失败尝试消耗了随机数”改变后续结果。

## 插件作者建议

1. 为每个独立领域机制创建稳定的命名流，不要复用无语义的共享流。
2. 把抽样用途写进 `purpose`，让调试和重演报告能解释结果。
3. 把随机流声明放在系统契约中，随插件版本和语义哈希一起审查。
4. 不要使用墙钟时间、线程顺序或容器迭代顺序作为随机种子或 tie-break。

## 与重演的关系

精确重演要求流身份、算法版本、根种子、位置、每次抽样和最终结果都保持一致。加载快照时，内核会验证流状态是否等于“初始种子经过指定次数抽样后的状态”；边界重演还会比较抽样证据的生产者、用途、因果和关联信息。
