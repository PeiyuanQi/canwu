参伍不把随机数当作一个全局、不可追踪的黑盒。随机性属于带命名、版本和所有者的流；每次抽样都会留下足够的证据，让相同运行环境可以重新得到相同结果。

## 随机流身份

一个 `RandomStreamKey` 由 `namespace`、`name` 和 `version` 组成，例如：

```text
canwu.core / knowledge-report-delay / 1
```

内核从运行根种子和流身份派生独立种子。不同领域使用不同流，因此报告延迟的抽样不会因为另一个系统增加了一次抽样而改变。流状态保存算法、初始种子、当前位置和生成器状态。

新建随机流使用 `SplitMix64V2` 的无偏拒绝采样。历史
`SplitMix64V1` 流仍保留旧的取模语义，以便旧日志按原含义重放。算法名称和版本
属于持久化契约；更换算法必须使用新的版本，不能悄悄改变既有流。

## 声明后才能抽样

边界系统只能使用自己在 `BoundarySystemContract.random_streams` 中声明并拥有的流。建立随机会话时，内核复制允许流的状态；未声明的流会被拒绝。

每次范围抽样都要求：

- 上界大于零；
- `purpose` 非空且已经规范化；
- 流位置可以安全递增。

插件只得到一个有界整数，不直接接触全局生成器状态。

## 操作定址随机抽样

对可能重试、回滚或跨阶段继续的机制，应使用
`random_sample_for_operation`。它除了随机流和范围，还把抽样绑定到稳定的
cause、operation ID、目标、occurrence 和 purpose。同一个权威操作因此不会因为
重试顺序变化而消费另一份随机结果。

随机决策策略也使用这条路径：`RandomOperationTarget::DecisionTicket` 绑定精确
票据版本，`DecisionOptionWeight` 把抽样区间映射到票据中已有的选项，
`ResolveDecisionRandomly` 再让内核为下一边界生成标准决策准入。在开票前选择的
另一种运行配置可以使用 LLM、Human 或 External selector，但已注册 controller 的
policy 不能在运行中替换；这些 selector 也不会替换天气、故障或疫情等随机世界事件。

## 抽样证据

每次抽样都会记录：

| 字段 | 含义 |
| --- | --- |
| 流与地址 | 哪一条版本化流，以及顺序位置或操作定址地址 |
| 上界与结果 | 请求的范围和实际值 |
| purpose | 这次抽样在领域中的语义用途 |
| producer | 边界系统或内核系统 |
| outcome | 例如边界决策或报告送达 |
| cause / correlation | 因果来源和处理链关联 |

抽样记录和流状态一起进入快照、边界证据和哈希。发生失败回滚时，流位置和抽样记录也一起恢复，避免“失败尝试消耗了随机数”改变后续结果。

## 重载、分支与反复试验

确定性重放不等于反存档作弊。相同的权威状态、命令或决策输入、插件语义环境和模拟时间，必须得到相同的抽样结果；因此从事件前的快照重新加载，不会让同一个事件自动重新掷骰子。

如果调用方从同一快照发出不同命令，`fork()` 或等价的分支入口可以产生合法的平行现实。这是新的平行现实，不是原运行的精确重放。是否把手动存档、单写入存档或研究分支开放给玩家，由上层应用的存档策略决定，不能通过改变随机种子来实现。

## 插件作者建议

1. 为每个独立领域机制创建稳定的命名流，不要复用无语义的共享流。
2. 把抽样用途写进 `purpose`，让调试和重放报告能解释结果。
3. 把随机流声明放在系统契约中，随插件版本和语义哈希一起审查。
4. 不要使用现实时间、线程执行顺序或容器迭代顺序作为随机种子或平局判定依据。
5. 不要把未知事实随机补全；把未知、角色选择、离散随机事件和群体比例结算分开建模。

## 与重放的关系

精确重放要求流身份、算法版本、根种子、顺序流位置、操作地址、每次抽样和最终结果都保持一致。加载快照时，模拟内核会验证顺序流状态是否等于“初始种子经过指定次数抽样后的状态”，并重算操作定址抽样；边界重放还会比较抽样证据的生产者、用途、因果和关联信息。
