> **Current contract.** The routing and transport types were introduced in 0.5 and remain part of the current 0.13.0 public API. Hosts must still provide network and historical content data. Since 0.13.0, the `canwu-movement` extension owns the lifecycle of the transport executions it admits and allocates capacity pools; map import, a universal historical dataset, and first-class simulation-core snapshot fields for transport records remain future work.

For a runnable end-to-end composition with addressed information delivery, see
[Routed correspondence from Wuxi](/en/tutorials/cases/routed-correspondence/).
That case uses the `canwu-correspondence` domain extension; this page continues
to explain the lower-level planning and execution contracts.

## Separate planning from execution

“How should a delivery travel from Wuxi to Beijing?” contains two different questions:

1. **Planning**: which route arrives earliest within the network, timetable, risk, and capacity constraints visible to this observer?
2. **Execution**: has the message loaded, departed, arrived at a relay, changed custody, rerouted after a disaster, and completed the recipient's delivery attempt?

`canwu-routing` answers the first question. `canwu-transport` records the second. Neither bypasses `canwu-sim` canonical ingress or writes directly into the `canwu-information` recipient ledger.

## Wuxi to Beijing

Planning is based on an observer-relative knowledge cut rather than an omniscient world read:

```rust
let request = RoutingRequest {
    origin: RoutingNodeRef::new("settlement/wuxi"),
    destination: RoutingNodeRef::new("settlement/beijing"),
    departure_at: SimTime::from_hours(8),
    policy: RoutingPolicy {
        allowed_modes: [TransferMode::Rail, TransferMode::Horse]
            .into_iter()
            .collect(),
        ..RoutingPolicy::default()
    },
};

let plan = plan_route(&planning_snapshot, &request)?;
```

`PlanningSnapshot` may come from the current-world adapter or from a rail, air, telegraph, or relay-station extension. It binds the observer, knowledge cut, topology version, and expiry. Someone with a current railway timetable and someone who only knows a courier rumor can therefore produce different valid plans.
To build a snapshot from exactly what one holder knows, use `planning_snapshot_from_holder_knowledge` from `canwu-correspondence`; see [Plan from a holder's knowledge](/en/developer/reading-state/#plan-from-a-holders-knowledge).

If a nearby recipient is served inside the same district, the plan may contain one short walking or horse leg. Beijing may require several relays, stations, and custody transfers. The router does not collapse both destinations merely because both are “another person.”

## ETA is not the delivery deadline

`RoutePlan.estimated_arrival_at` is an execution estimate. `DeliveryAttempt.due_at` is the logical completion deadline in the information lifecycle. A late ETA must not silently rewrite the original deadline; the system records failure or creates a new retry attempt.

Rerouting and retrying are also different:

- **reroute**: create a new immutable `ItineraryRevision` for the same delivery attempt;
- **retry**: create a new delivery-attempt version, which may choose a new plan and mode.

## Rail, air, telegraph, and relay stations

Historical differences belong in network data instead of four copied routing algorithms:

- Rail uses `TransferMode::Rail`, station nodes, departure slots, and capacity bookings. 1900 and 1940 use different content packages and timetables.
- Air uses `TransferMode::Air`, airports, flight slots, weather availability, and bookings.
- Telegraph or other signals use `TransferMode::Signal`; office hours, latency, risk, and interception are data or extension policy.
- Ancient courier networks use relay-station nodes, horse/foot traversal, and explicit custody handoffs.

Fixed durations, departure schedules, and time-dependent durations use `Fixed`, `Departures`, and `Piecewise` traversal models. A non-FIFO network must explicitly select the bounded label-correcting algorithm; the default FIFO network uses deterministic Dijkstra.

## Execution and disasters

After planning, the host installs the plan into a transport execution and creates the completion bridge for the information attempt:

```rust
let mut execution = TransportExecution::new(
    TransportExecutionId(7),
    Some(delivery_attempt_version.clone()),
);
execution.install_initial_itinerary(initial_revision)?;
execution.begin_saga(
    delivery_attempt_version,
    delivery_completion_operation_key(
        TransportExecutionId(7),
        ItineraryRevisionId(1),
        1,
    ),
)?;
```

Each leg has its own status and actual departure/arrival times. At a relay, record a `Handoff` before starting the next leg. If flood, war, weather, or a line outage blocks the route, a domain system records the failure and reason; execution enters `ReplanPending`, and a new planning snapshot produces a successor itinerary revision. The replacement revision also records custody transfer from the failed segment into its first segment. Incidents outside an active transport attempt are retained as suppressed evidence rather than mutating an information or arrival-pending transition. The router never invents the disaster.

After the final leg arrives, execution enters `ArrivalPending`. `completion_request()` yields a stable operation key and evidence; the host submits it through canonical ingress to complete the information attempt. Repeating the same key must not complete the attempt twice.

## People, seizures, and external conditions

Since 0.12.0 (`canwu-transport.v4`), three record additions cover common strategy-game movement:

- `MovementSubjectRole::PersonsGroup` moves a persons group, several people travelling as one subject, usually identified by an application domain record. Like cargo, it must carry a positive quantity, here the head count; `requires_quantity()` states the rule.
- `HandoffKind::Seizure { by }` records a seizure handoff: custody taken by someone outside the itinerary, such as bandits or a hostile garrison. It follows the same leg rules as a planned handoff. Since `canwu-transport.v5`, a seizure may also be terminal: it names a failed leg of the active revision as both ends, and custody leaves the itinerary. Only one terminal seizure is allowed. Afterwards the execution can no longer fail or reroute a leg, arrive, settle, book capacity, or record another handoff; its owner must close it as failed or cancelled. Ordinary handoffs stay planned handoffs (`Planned`) and serialize as before.
- `ItineraryRevisionReason::ExternalCondition { record, version, kind }` explains a reroute by an external condition, citing an application-owned condition record, such as a flood or border-closure record, at an exact version with an application label. It is validated for the initial itinerary and for every reroute.

Transport records these facts only. Whether a seizure or hazard happened, and who had the authority, stays in application systems.

## Movement lifecycle and capacity pools

`canwu-transport` stays a record library. Since 0.13.0, the movement lifecycle extension `canwu-movement` owns the lifecycle of those records, so a host no longer drives every leg by hand. Register `MovementPlugin::new(evidence_kinds)` with the application record kinds it may read, such as authority records, delivery attempts, external-condition records, and incident evidence; that list is its exact read set.

- **Orders.** The tracked command `apply_movement_operation_v1` carries a `MovementCommandV1` from the issuer's own holder. An `Order` admits a `MovementOrder` and creates its execution. The acting holder becomes the owner, and an optional operator and delayed remote observers receive report grants. Moving anyone but the owner needs an `authority_basis`: the current version of a declared application record that names the owner under the `movement_grantee` role and every other subject under `movement_subject`.
- **Legs.** Each leg settles at its due time through the internal `movement_leg_due_v1` ingress, while `StartLeg`, `CompleteLeg`, `FailLeg`, `Reroute`, `RecordHandoff`, and `Cancel` act explicitly. Arrival on the final leg settles the execution, or enters `ArrivalPending` when a delivery attempt is attached.
- **Incidents.** Application systems report failures, reroutes, seizure handoffs, and delivery reconciliation through the public `movement_incident_v1` ingress, citing an exact evidence record of a declared kind. The plugin never draws randomness; the roll for a hazard belongs to your system.
- **Capacity pools.** An `OfferPool` operation offers a capacity pool (`TransportCapacityPoolV1`): a windowed quantity of interchangeable capacity such as ferry crossings or relay mounts. `RequestBooking` asks for capacity for one unstarted leg inside its planned window. In phase 7, one booking-allocation pass per pool confirms every booking requested in that boundary in full or fails it with recorded evidence, ordered by priority, window start, tie-break key, admission sequence, and booking identity; confirmed capacity is never preempted. A departing leg consumes its bookings, a leg whose booking failed or expired fails with `capacity_unavailable` and waits for a reroute, and a confirmed booking whose window has not opened delays the departure.
- **Reports.** The plugin publishes `canwu.movement/movement_report` knowledge to living person holders. The owner and operator see the current execution, a delayed remote observer sees coarse progress as it stood one delay earlier, and a holder without a grant sees nothing.

Every operation key has one durable outcome, so an exact retry is a no-op. A closed execution retires from the runtime once its final reports are out, and at most 365 days after it closed; published reports and the record history keep what happened. The allocation function `allocate_capacity_bookings` is public and pure, so a host that runs its own lifecycle can reuse the same ordering. See the crate [README](https://github.com/PeiyuanQi/canwu/blob/main/crates/extensions/canwu-movement/README.md) for limits and error codes.

## Capacity and determinism

Trains, aircraft, relay horses, and telegraph lines can use `CapacityBooking`. A booking is a persistent windowed record with requested, confirmed, consumed, released, expired, cancelled, and failed states; since `canwu-transport.v5` it may be confirmed, failed, or cancelled before its window opens but consumed only inside it. A route-cache hit must never hide a capacity mutation. Movement executions can draw on capacity pools as described above, but the current correspondence contract still exposes only `CorrespondenceCapacityAdmission::Unconstrained` and cannot start a constrained leg. A future admission variant must carry exact booking or simulation-reservation evidence supplied by an application or infrastructure adapter.

`RoutingCache` is derived from the planning-snapshot digest, request, and policy. It is rebuildable, excluded from snapshots, and unnecessary for exact replay. Expansion, transfer, risk, and arrival-horizon limits are also policy inputs, so “no route” and “budget exceeded” are deterministic replayable outcomes.
