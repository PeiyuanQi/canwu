## 1. What problem are we solving?

Imagine that you are building a historical simulation set during a period of
competing warlords. Warlord A is already fighting and asks neighboring Warlord B
to send troops. At first, Warlord B knows that they share an enemy but cannot
confirm that the supply route is safe. Only after new intelligence arrives
should “send aid” become an actionable choice.

The goal is not simply to make an AI return yes or no. You need a decision chain
that can safely enter the live simulation:

- update the available choices when the known facts change;
- allow an AI, player, or external model to select only an existing option,
  never invent an arbitrary command;
- turn the selected aid option into a command under the controller's persisted
  authority;
- record attempts, scores, and outcomes so restoration and exact replay never
  have to ask the decision maker again.

The scenario does not represent specific historical people. Personality,
intelligence sources, and the historical meaning of “worth aiding” remain
domain concerns. Canwu provides the boundaries among decisions, authority,
commands, and durable evidence.

## 2. How does the example work?

The example composes several systems:

| System | Role in this example | Related documentation |
| --- | --- | --- |
| Decision tickets, controllers, and policies | Store the question, current options, decision identity, and scoring process | The walkthrough below |
| Authority and command ingress | Turn the selected option into a validated command | [Architecture overview](/en/architecture/), [Integrate and drive the simulation](/en/developer/integration/) |
| Settlement boundary | Admit decision ingress, persist the trace, and execute the derived command | [Settlement system](/en/architecture/settlement/) |
| Actor-relative information | Build context from facts visible to Warlord B instead of leaking omniscient state | [Read and present state safely](/en/developer/reading-state/) |
| Persistence and exact replay | Retain tickets, attempts, traces, and command evidence | [Save, replay, and fork](/en/developer/persistence/) |

Start by running the example:

```shell
cargo run -p canwu-api --example decision_ticket
```

The program prints a complete `DecisionTrace`. `WeightedUtilityPolicy`
selects `send-aid`, and the trace records both the total score and each factor's
contribution for every option. The example then restores a snapshot and runs an
exact replay, proving that both paths produce the same final snapshot.

### Implementation path

```text
facts visible to Warlord B
  -> open a DecisionTicket
  -> new intelligence arrives; ReplaceOptions
  -> utility policy selects an existing option ID
  -> controller derives issuer and authority
  -> ordinary Command validation and execution
  -> persisted DecisionTrace
```

<Steps>
1. Register the `warlord-b-ai` controller and bind it to a policy identity, responsible actor, and controllable army.
2. Open the aid-request ticket. The supply route is not confirmed, so declining is the only initial option.
3. Once the route is confirmed, use `DecisionMutation::ReplaceOptions` to update the context and add `send-aid`.
4. Use `WeightedUtilityPolicy` to calculate deterministic integer scores for the current options.
5. Call `drive_decision()` to enqueue a resolution. The next canonical boundary persists the trace and submits the selected command through ordinary command admission.
6. Save, restore, and exactly replay the run without invoking the policy again.
</Steps>

### Step one: bind decision identity to action authority

```rust
let controller = DecisionControllerBinding::new(
    "warlord-b-ai",
    DecisionPolicyIdentity::new(
        DecisionPolicyKind::Utility,
        "aid-utility",
        "1",
    ),
    DecisionAuthority::Actor { actor: ids.commander },
)
.with_command_subject(EntityRef::Army(ids.army));
```

The controller is not the domain AI's “brain.” It persists three things: who
decides, which policy is used, and whose authority may control which subject
after an option is selected. The policy receives no issuer, seat, permission
profile, or mutable world reference.

### Step two: store one explicit question in a ticket

`DecisionTicketDraft` contains a stable definition, decision maker,
controller, deadline, explicit context, and current options. The example starts
with only `decline`:

```rust
DecisionMutation::Open {
    ticket: DecisionTicketDraft {
        id: DecisionTicketId::new(1),
        definition: "beiyang.request-military-aid".to_owned(),
        decision_maker: EntityRef::Person(ids.commander),
        assigned_controller: "warlord-b-ai".to_owned(),
        summary: "Neighboring warlord requests immediate military aid".to_owned(),
        context: DecisionContext::new(
            "beiyang.aid-request.v1",
            json!({ "common_enemy": true }),
        ),
        options: vec![DecisionOption::new("decline", "Decline aid")],
        deadline: Some(now + SimDuration::days(2)),
    },
}
```

A production application should construct this context from Warlord B's
knowledge or observations. It should not hand omniscient world state to the
policy.

### Step three: change the options when new intelligence arrives

Route confirmation is a new authoritative fact, so the application submits an
option replacement guarded by `expected_version`:

```rust
DecisionMutation::ReplaceOptions {
    ticket_id: DecisionTicketId::new(1),
    expected_version: 1,
    context: DecisionContext::new(
        "beiyang.aid-request.v1",
        json!({ "common_enemy": true, "route_confirmed": true }),
    ),
    options: vec![decline, send_aid],
}
```

The ticket version increments. If a Human, External, or LLM policy submits a
response for the previous version, Canwu rejects it instead of applying a stale
answer to the new option set.

The `send-aid` option may contain a serialized existing Canwu command, but the
policy can return only the option ID. The runnable `canwu-api` example below is
an intentional compatibility fixture, so it uses the retained legacy
`Command::OrderMovement` variant while exercising the generic decision kernel:

```rust
DecisionOption::new("send-aid", "Send the neighboring army").with_command(
    serde_json::to_value(Command::OrderMovement {
        subject: EntityRef::Army(ids.army),
        destination: ids.eastern_territory,
        cargo: Vec::new(),
    })?,
)
```

New applications should encode `MovementCommand` through
`canwu-reference-world`, or define an equivalent plugin command in their own
domain crate. See [Move an army](/en/tutorials/move-army/) for the current
integration path. Decision tickets accept either form because they persist a
serialized command selected under the controller's authority.

### Step four: explain why the utility policy sends aid

```rust
let policy = WeightedUtilityPolicy::new(
    "aid-utility",
    "1",
    UtilityProfile {
        weights: BTreeMap::from([
            ("alliance".to_owned(), 3),
            ("home_defense".to_owned(), 1),
        ]),
    },
);
```

Each option supplies domain-defined integer inputs. The generic evaluator
computes `value * weight`, resolves ties by stable option ID, and records each
factor's contribution in the trace. The engine does not understand the
historical meaning of alliance credibility or home defense; those meanings and
weights belong to the domain or policy.

### Step five: let the policy choose and the controller act

```rust
canwu.drive_decision(
    canwu.time(),
    0,
    DecisionRequestId::new(4),
    Some(CommandRequestId::new(1)),
    DecisionTicketId::new(1),
    &policy,
)?;
canwu.step_canonical()?;
```

Two boundaries remain in place:

- The policy can select only an existing, unblocked ticket option.
- The controller derives command authority from its persisted binding; the
  command still passes Canwu's ordinary authority, revision, time, and domain
  validation.

Replacing the utility policy with a player, external service, or LLM therefore
does not grant arbitrary command creation or a way to forge Warlord B's
authority.

### Step six: persist the trace and reuse it during replay

`decision_attempts()` returns the accepted or rejected result of every
canonical admission. A stale revision, stale ticket version, or closed ticket
becomes a persisted rejection instead of repeatedly rolling back and blocking
the simulation. `decision_traces()` returns successful outcomes, ticket
versions, policy identities, utility breakdowns, external evidence, and command
request IDs.

Snapshots retain controllers, tickets, current options, deadlines, attempts,
and traces. Exact replay consumes the recorded decision ingress, decision
attempt, and command attempt; it never asks the player, external service, or
model to decide again. To compare another policy, fork from a snapshot and
create new decision ingress. That is a counterfactual branch, not exact replay.

You can substitute several decision styles:

- `WeightedUtilityPolicy` for deterministic strategic, personality, or doctrine scores;
- `OrderedRulePolicy` for ordered selection or deferral rules;
- `QueuedHumanPolicy` for a UI or player response bound to the ticket version;
- `QueuedExternalPolicy` for a host adapter that calls an external decision service;
- `QueuedLlmPolicy` for model selection over context and option descriptions without exposing command actions.
