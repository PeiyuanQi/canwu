Canwu is a headless historical simulation core. A client may be a game, research tool, debug UI, or agent, but every client reaches the simulation through the same public boundaries instead of receiving a mutable reference to the live world.

## Format 7 and three simulation granularities

Before 1.0, 0.7 uses a clean persistence break: snapshots and `ReplayJournal`
carry declared run identity, initial scenario, commitments, authority root, and
complete evidence. The kernel does not silently load format 2-6 saves.
`SimulationGranularity` defines only the domain-neutral levels `aggregate`,
`group`, and `actor`. Celestial Mandate may map them to Population, Special
Group, and Character in its own reference integration; Southern Ming and WWII
are CM content and ruleset integrations, not Canwu kernel modules.

## From client to kernel

| Layer | Responsibility | Public contract |
| --- | --- | --- |
| Client | Maps, rendering, input, research workflows, and agent loops | Choose the interface freely; do not own authoritative state |
| `canwu-api` | Programmatic API, commands, domain records, events, snapshots, and replay | Work through validated public ingress |
| `canwu-sim` | Scheduling, plugins, settlement, persistence, and replay | The only owner of live mutable simulation state |
| Foundation and model crates | IDs, time, events, decisions, and actor knowledge | Serializable, portable engine contracts |

## Five architectural boundaries

1. **Command boundary:** external changes enter through validated engine commands, domain plugin commands, or canonical ingress; clients never rewrite state directly.
2. **Read boundary:** the public API returns generic entities, domain records, and evidence; integrations build detached projections, while `CanwuViewer` scopes actor knowledge.
3. **Determinism boundary:** time, queues, plugin order, allocation, and random streams all have explicit canonical ordering.
4. **Plugin boundary:** systems declare reads, writes, phases, resources, and random streams before the kernel validates and runs them.
5. **Evidence boundary:** commands, events, settlement, random draws, state changes, and hashes form an inspectable replay record.

## How one action moves through the system

<Steps>
1. A client or domain integration submits a typed command through `canwu-api`; the kernel validates authority, preconditions, revision, and request identity.
2. An accepted command emits a causally linked event and schedules follow-up work using representable simulation time.
3. In a transaction, the simulation core cuts the admission set and immutable snapshot, then runs systems in fixed phase order.
4. Systems propose reservations, state changes, domain records, and events; the kernel validates declared access and commits atomically.
5. The boundary stores events, random draws, allocations, changes, producer provenance, and hashes before clients read snapshots or actor-scoped observations.
</Steps>

| `canwu-debug` | Reference client using the public API and reference-world integration |

The published `canwu-culture` culture system SDK sits above
`canwu-society`, not in the simulation core. It compiles versioned content into
an externally immutable, content-hash-bound execution plan, enforces cardinality and
expanded fan-out budgets, and provides dirty-set and hot-target indexes. Its
complete state restores lifecycle schedules, hot/dirty indexes, and effect
cadence. Dormant targets leave the culture hot index and stop compiled culture transition rules
after explicit society synchronization; retired targets additionally release
target-scoped dynamic society state while historical evidence remains available.
Boundary-system registration, canonical signal admission, and incremental
aggregation remain follow-up work. See the standalone [culture and legal institutional systems](/en/architecture/culture-law/),
which combines culture authoring, lifecycle, and legal institutionalization design.

## From domain extensions to runnable kits

Canwu provides more than kernel contracts. Generic domain extensions provide
reusable mechanics, reference content packs provide replaceable domain data,
reference integrations connect those capabilities to a small world, and
starter kits compose them into vertical slices developers can run and extend.
All of these layers remain above the kernel; no historical world is embedded in
`canwu-core`.

`canwu-correspondence` is a domain extension by ownership: it owns
communication demand, address resolution, accepted routes, disaster and
interception policy, and cross-mechanism evidence. It is also a
`SimulationPlugin` by execution form, registering authoritative commands,
canonical ingress, and boundary systems. It depends on `canwu-api` and
`canwu-information`, with no reverse dependency, so the crate DAG stays acyclic.

Reference content packs are data, not new solvers. Reference integrations must
use the public API and be replaceable by another world or economy model. Starter
kits must demonstrate scenario creation, commands, settlement, actor-relative
reads, save/load, forks, and exact replay. The collection is expected to grow;
it is not a privileged path for one fixed demo.
