Canwu is a headless historical simulation core. A client may be a game, research tool, debug UI, or agent, but every client reaches the simulation through the same public boundaries instead of receiving a mutable reference to the live world.

## From client to kernel

| Layer | Responsibility | Public contract |
| --- | --- | --- |
| Client | Maps, rendering, input, research workflows, and agent loops | Choose the interface freely; do not own authoritative state |
| `canwu-api` | Programmatic API, queries, semantic actions, events, and snapshots | Work through validated commands and queries |
| `canwu-sim` | Scheduling, plugins, settlement, persistence, and replay | The only owner of live mutable simulation state |
| Foundation crates | IDs, time, events, world, and actor knowledge | Serializable, portable building blocks |

## Five architectural boundaries

1. **Command boundary:** external changes enter through validated commands, semantic actions, or canonical ingress; clients never rewrite the world directly.
2. **Read boundary:** the programmatic API returns detached snapshots, while the semantic API builds observations from an actor's knowledge.
3. **Determinism boundary:** time, queues, plugin order, allocation, and random streams all have explicit canonical ordering.
4. **Plugin boundary:** systems declare reads, writes, phases, resources, and random streams before the kernel validates and runs them.
5. **Evidence boundary:** commands, events, settlement, random draws, state changes, and hashes form an inspectable replay record.

## How one action moves through the system

<Steps>
1. A client submits a command or semantic action through `canwu-api`; the kernel validates authority, preconditions, and request identity.
2. An accepted action emits a causally linked event and schedules follow-up work using representable simulation time.
3. At a settlement boundary, the kernel cuts the admission set and immutable snapshot, then runs systems in fixed phase order.
4. Systems propose reservations, state changes, domain records, and events; the kernel validates declared access and commits atomically.
5. The boundary stores events, random draws, allocations, changes, producer provenance, and hashes before clients read snapshots or actor-scoped observations.
</Steps>

## Workspace crates

| Crate | Core responsibility |
| --- | --- |
| `canwu-core` | Typed IDs, deterministic random utilities, and schema metadata |
| `canwu-time` | Historical timestamps and checked duration arithmetic |
| `canwu-event` | Serializable events and compact causal provenance |
| `canwu-world` | Historical entities and read-only snapshots |
| `canwu-knowledge` | Actor knowledge, source, confidence, and information age |
| `canwu-sim` | Private runtime, scheduling, plugins, and settlement |
| `canwu-api` | Programmatic and semantic interfaces |
| `canwu-debug` | Reference client using only the public API |
