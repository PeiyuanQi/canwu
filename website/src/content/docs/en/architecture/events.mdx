Canwu events are serializable, inspectable causal records. They are not UI notifications and not a mutable client-owned log; they belong to the authoritative evidence chain used by snapshots, boundary records, and exact replay.

## What an event contains

Every `SimEvent` contains:

| Field | Meaning |
| --- | --- |
| `id` | Monotonic stable event identity |
| `timestamp` | Simulation time at which the event occurs |
| `kind` | Structured event type and payload |
| `affected_entities` | Entities affected by the event |
| `summary` | Short explanation for tools and debug surfaces |
| `cause` | Command, event, boundary, or system that produced it |
| `correlation_id` | Correlates evidence from one processing chain |

`EventKind` itself owns no domain-event enum. It stores only a stable `type` tag and flattened structured fields. A domain or integration can define a typed payload in its own crate, encode it with `from_payload`, and recover it with `decode_payload`. Format 7 established the current tags and canonical field order; Format 8 preserves them while rejecting pre-8 persistence. New domain events belong to their plugin and declare provenance, audience, and boundary ownership through registration contracts.

## Causal chain

`CauseRef` expresses four sources:

- `Command`: accepted external engine command or domain command;
- `Event`: a previously recorded event;
- `Boundary`: a system running in a transaction;
- `System`: a kernel or controlled plugin system.

A plugin-owned domain action can form this evidence chain:

```text
plugin command
  └─ typed domain event
       └─ scheduled plugin work
            ├─ domain-state change
            ├─ follow-up domain event
            └─ actor-scoped report
                 └─ knowledge publication
```

Every link retains time, entities, cause, and correlation, so a debug surface can explain what happened and replay can check why it happened in that order.

## Scheduling and admission

Internal scheduled work is ordered by `(simulation timestamp, insertion sequence)`. Host-facing canonical ingress is ordered by due time, ingress class, descending priority, issue time, and ingress ID; classes are command, communication, acknowledgement, information, and scheduled system. Since 0.12.0, the issuer of a queued plugin item can withdraw it before it is due; the withdrawal is its own terminal ingress record, and the withdrawn item is never admitted (see [plugin ingress cancellation](/en/developer/integration/#withdraw-queued-plugin-input)).

Since 0.13.0, a plugin whose authoritative writer runs on a coarser cadence can queue what it admits. `canwu-society` and the culture boundary plugin admit packets through event-driven phase-12 intake systems and apply them at their next Daily or Monthly settlement, while `canwu-movement` settles each leg through the internal scheduled ingress `movement_leg_due_v1`. See [where the 0.13.0 extension systems run](/en/architecture/settlement/#where-the-0130-extension-systems-run).

Late input is rejected instead of being inserted behind a committed boundary. A zero-delay packet generated by a boundary waits until the current admission cut closes and enters the next boundary at the same simulation time.

## Event opportunities and expiry settlement

Large event systems should not scan every entity and roll a temporary die every frame. A domain plugin can create persistent event opportunities when state changes, admitted events, or declared time cadences make them eligible, then schedule each opportunity at a deterministic due time. At expiry, the plugin settles only due candidates and writes the random stream, causal source, deduplication key, cooldown, and outcome into boundary evidence.

Opportunity generation, event-result settlement, and actor-scoped report publication are three separate steps. The same candidate keeps the same result after reload; different commands or decisions can create a new valid alternative reality from the same checkpoint.

## Events and actor knowledge

Authoritative domain state and actor knowledge are separate stores. After an army arrives, a commander may know the new location immediately, while a distant actor updates only after a report is delivered. `CanwuViewer` queries only the bound holder's knowledge and never exposes a trusted domain projection to that client.

## Boundary events and replay

Events emitted by boundary systems enter the next boundary's event admission and do not invoke legacy immediate reactors. Each successful boundary stores events, commands, ingress, random draws, changes, producer, phase, visibility, and hashes; loading and replay recompute and compare the complete evidence.

## Evaluation traces and transition audits are evidence, not events

Since 0.13.0, boundary records carry two more kinds of evidence beside events. An [evaluation trace](/en/architecture/settlement/#evaluation-traces) explains how an application rule produced one result for one subject, and a [transition audit](/en/architecture/settlement/#transition-manifests) records how a transition manifest settled. Neither is a `SimEvent`, and neither is state: no system reads a trace back, and an audit is read-only evidence for phase-12 systems. Both are hashed into the boundary chain and replayed with it.

A holder sees a trace only through `CanwuViewer::evaluation_traces`: traces about its own entity, and traces about another subject that were evaluated after a knowledge publication naming that subject reached its ledger. Research and developer principals see every trace; a public principal's read is refused with `InvalidKnowledgeAuthority`.
