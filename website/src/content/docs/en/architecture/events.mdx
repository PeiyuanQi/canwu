Canwu events are serializable, inspectable causal records. They are not UI notifications and not a mutable client-owned log; they belong to the authoritative evidence chain used by snapshots, boundary records, and exact replay.

## What an event contains

Every `SimEvent` contains:

| Field | Meaning |
| --- | --- |
| `id` | Monotonic stable event identity |
| `timestamp` | Simulation time at which the event occurs |
| `kind` | Structured event type and payload |
| `affected_entities` | Entities affected by the event |
| `summary` | Short explanation for tools and debug surfaces |
| `cause` | Command, event, boundary, or system that produced it |
| `correlation_id` | Correlates evidence from one processing chain |

Core event kinds include `MoveOrdered`, `PersonMoveOrdered`, `ArmyArrived`, `PersonArrived`, `LetterDelivered`, `ReportDispatched`, `KnowledgeUpdated`, `DebugFieldChanged`, and plugin events. Plugins may add event kinds through a registered contract that declares provenance and boundary ownership.

## Causal chain

`CauseRef` expresses four sources:

- `Command`: accepted external command or semantic action;
- `Event`: a previously recorded event;
- `Boundary`: a system running in a settlement boundary;
- `System`: a kernel or controlled plugin system.

A movement example can form this evidence chain:

```text
OrderMovement command
  └─ MoveOrdered or PersonMoveOrdered event
       └─ scheduled ArmyArrival or PersonArrival work
            ├─ ArmyArrived or PersonArrived event
            ├─ LetterDelivered event
            └─ ReportDispatched event
                 └─ KnowledgeUpdated event
```

Every link retains time, entities, cause, and correlation, so a debug surface can explain what happened and replay can check why it happened in that order.

## Scheduling and admission

Internal scheduled work is ordered by `(simulation timestamp, insertion sequence)`. Host-facing canonical ingress is ordered by due time, ingress class, descending priority, issue time, and ingress ID; classes are command, communication, acknowledgement, information, and scheduled system.

Late input is rejected instead of being inserted behind a committed boundary. A zero-delay packet generated by a boundary waits until the current admission cut closes and enters the next boundary at the same simulation time.

## Event opportunities and expiry settlement

Large event systems should not scan every entity and roll a temporary die every frame. A domain plugin can create persistent event opportunities when state changes, admitted events, or declared time cadences make them eligible, then schedule each opportunity at a deterministic due time. At expiry, the plugin settles only due candidates and writes the random stream, causal source, deduplication key, cooldown, and outcome into boundary evidence.

Opportunity generation, event-result settlement, and actor-scoped report publication are three separate steps. The same candidate keeps the same result after reload; different commands or decisions can create a new legal branch from the same checkpoint.

## Events and actor knowledge

World truth and actor knowledge are separate stores. After an army arrives, a commander may know the new location immediately, while a distant actor first receives `ReportDispatched` and later a `KnowledgeUpdated` event. The semantic API returns only event changes and knowledge records visible to the requesting actor; it never exposes omniscient state to a client.

## Boundary events and replay

Events emitted by boundary systems enter the next boundary's event admission and do not invoke legacy immediate reactors. Each successful boundary stores events, commands, ingress, random draws, changes, producer, phase, visibility, and hashes; loading and replay recompute and compare the complete evidence.
