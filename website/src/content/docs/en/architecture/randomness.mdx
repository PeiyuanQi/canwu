Canwu does not treat randomness as one global, untraceable black box. Randomness belongs to named, versioned streams with explicit owners; every draw leaves enough evidence for the same run environment to produce the same result again.

## Stream identity

A `RandomStreamKey` contains a `namespace`, `name`, and `version`, for example:

```text
canwu.core / knowledge-report-delay / 1
```

The kernel derives an independent seed from the run root seed and stream identity. Separate domains use separate streams, so adding a report-delay draw cannot shift an unrelated system's sequence. Stream state stores the algorithm, initial seed, position, and generator state.

New streams use `SplitMix64V2` with unbiased rejection sampling. Historical
`SplitMix64V1` streams retain their modulo semantics so old journals replay with
their original meaning. Algorithm name and version are part of the persistence
contract; changing an algorithm requires a new version rather than silently
changing an existing stream.

## Declare before drawing

A boundary system may use only streams declared and owned in `BoundarySystemContract.random_streams`. When a random session starts, the kernel copies the allowed stream states; undeclared streams are rejected.

Every range draw requires:

- a positive upper bound;
- a non-empty, canonical `purpose` string;
- a stream position that can be incremented safely.

A plugin receives a bounded integer, not the global generator state.

## Operation-keyed random draws

Mechanics that may retry, roll back, or continue across phases should use
`random_sample_for_operation`. In addition to stream and range, it binds the
draw to stable cause, operation ID, target, occurrence, and purpose. The same
authoritative operation therefore cannot consume a different sample merely
because retry order changed.

Random decision policy uses this path too:
`RandomOperationTarget::DecisionTicket` binds an exact ticket version,
`DecisionOptionWeight` maps the draw interval to existing ticket options, and
`ResolveDecisionRandomly` lets the kernel generate ordinary decision ingress
for the next boundary. Another run configuration selected before ticket opening
may use LLM, Human, or External selection, but a registered controller policy
cannot be replaced at runtime. These selectors also do not replace stochastic
world events such as weather, failure, or epidemic incidents.

## Draw evidence

Every draw records:

| Field | Meaning |
| --- | --- |
| Stream and address | Which versioned stream, plus a sequential position or operation-keyed address |
| Bound and value | Requested range and returned value |
| `purpose` | Semantic reason for the draw |
| `producer` | Boundary system or core system |
| `outcome` | For example a boundary decision or report delivery |
| cause / correlation | Causal source and processing-chain correlation |

Draw records and stream state enter snapshots, boundary evidence, and hashes. On rollback, stream positions and draw records roll back together, so a failed attempt cannot consume randomness and alter later results.

## Reloading, alternative realities, and repeated trials

Deterministic replay is not the same as save-scumming. The same authoritative state, command or decision input, plugin semantic environment, and simulation time must produce the same draw result; reloading a snapshot from before an event does not automatically roll the same event again with a different outcome.

If a caller issues a different command from the same snapshot, `fork()` or an equivalent fork entry can produce a valid alternative reality. That is a new alternative reality, not an exact replay of the original run. Whether to expose manual saves, single-writer saves, or research forks to players belongs to the application's save policy, not to a changed random seed.

## Guidance for plugin authors

1. Give each independent domain mechanic a stable named stream; do not reuse an unscoped shared stream.
2. Put the semantic reason in `purpose` so debug and replay output can explain the result.
3. Review stream declarations with the plugin version and semantic hash.
4. Never use wall-clock time, thread order, or container iteration order as a seed or tie-break.
5. Do not randomize missing facts; model unknown knowledge, actor choices, discrete incidents, and aggregate-rate settlement separately.

## Replay contract

Exact replay requires stream identity, algorithm version, root seed, sequential positions, operation addresses, every draw, and final outcomes to match. When loading a snapshot, the kernel verifies sequential stream state against the initial seed advanced by the recorded draw count and recomputes operation-keyed samples; boundary replay also compares producer, purpose, cause, and correlation for each draw.
