Use this page to save and load a run, keep compact history for a long-running simulation, replay a run exactly, or fork from a saved point to try different inputs.

A Canwu save holds more than world data. It also carries the commands, events, boundary records, random draws, plugin semantic environment, and state commitments that let a load verify the state. The **plugin semantic environment** is the name, version, and semantic hash of every plugin in the run; loading and replay need a plugin set that matches it.

A restored or replayed run has the same `checkpoint_hash()` as the original. A fork starts from the same state and then diverges.

## Choose the recovery goal

| Goal | Save with | Load with | Your application's job |
| --- | --- | --- | --- |
| Normal save or service restart | `snapshot_json()` | `Canwu::from_snapshot_json_with_plugins()` | Store the whole snapshot; pass the same plugin set when loading |
| Compact storage for a long run | `checkpoint_journal_json()` | `Canwu::from_checkpoint_journal_json_with_plugins()` | Store the checkpoint and the unbroken journal after it |
| Incremental saves that store only changed state | `prepare_paged_checkpoint()` | `Canwu::from_paged_checkpoint_and_journal_with_plugins()` | Keep every state page and the unbroken evidence prefix; see [paged checkpoints](#paged-checkpoints) |
| Audit or exact reconstruction | `replay_journal()` | `Canwu::replay_from_journal()` or `replay_from_journal_json()` | Store the whole journal and keep a matching plugin set |
| Send effects to outside systems | `outbox_entries()` | — | Deliver at least once, deduplicate by `delivery_id`, and store acknowledgement state |
| Try different inputs from one point | `fork()` | — | Treat the fork as a new alternative reality |

## Save and restore a snapshot (excerpt)

```rust
use canwu_api::Canwu;
use canwu_reference_world::{ReferenceWorldPlugin, demo_scenario};

let (scenario, _) = demo_scenario()?;
let plugin = ReferenceWorldPlugin;
let canwu = Canwu::new_with_plugins(35, scenario, &[&plugin])?;

let json = canwu.snapshot_json()?;
let restored = Canwu::from_snapshot_json_with_plugins(&json, &[&plugin])?;
assert_eq!(restored.checkpoint_hash(), canwu.checkpoint_hash());
```

Loading validates the snapshot, including its format, engine version, and plugin descriptors, and fails if anything does not match. Once a save contains plugin domain records, pass the same plugins to load it.

The [`starter` example](https://github.com/PeiyuanQi/canwu/blob/main/crates/integrations/canwu-reference-world/examples/starter.rs) runs this together with forking and exact replay:

```shell
cargo run -p canwu-reference-world --example starter
```

## Checkpoint journals and exact replay

A **checkpoint journal** (`CheckpointJournal`) bundles a validated checkpoint with the unbroken evidence that follows it. It suits long runs because it starts from the checkpoint and carries only the evidence recorded after it.

**Exact replay** rebuilds the same run from the journal's initial scenario, inputs, and recorded evidence:

```rust
let checkpoint_journal = canwu.checkpoint_journal_json()?;
let from_checkpoint =
    Canwu::from_checkpoint_journal_json_with_plugins(&checkpoint_journal, &[&plugin])?;
assert_eq!(from_checkpoint.checkpoint_hash(), canwu.checkpoint_hash());

let journal = canwu.replay_journal();
let replayed = Canwu::replay_from_journal(&[&plugin], &journal)?;
assert_eq!(replayed.checkpoint_hash(), canwu.checkpoint_hash());
```

Rules for exact replay:

- The scenario comes from the journal; `replay_from_journal()` takes only the plugins and the journal.
- Run identity, engine version, plugin semantic environment, and recorded evidence must all match.
- Replay reuses recorded outcomes. Decisions, random draws, and external answers are read from the journal, and side effects are not sent again.

## Alternative realities

`fork()` copies the run at its current point into an independent simulation. Use it to compare another command sequence, policy, or research assumption. The fork advances through the normal command and time APIs, and once its inputs differ it is a new *alternative reality*, separate from exact replay of the original.

## Deliver outside effects: the outbox

Boundary emissions meant for outside systems appear in `outbox_entries()`. Each `OutboxEntry` has a stable `delivery_id` derived from the run, boundary, event, and emission index.

1. Store each `delivery_id` with its delivery and acknowledgement state in your own storage.
2. Deliver at least once, so a timeout or restart can retry safely.
3. Deduplicate by `delivery_id` on the receiving side; a network call may happen more than once.
4. Exact replay regenerates the same `delivery_id` values and leaves delivery to you.

In compact mode (`CompactedCanwu`), `seal_evidence()` returns the sealed `EvidenceJournalSegment`. Keep that segment with your delivery and acknowledgement state. Sealing or compacting evidence does not mark an effect as delivered or acknowledged.

## Advanced storage and archives

Paged checkpoints, `StatePageProvider`, decision-history archives, and plugin archive participants matter only once snapshot size or hot-history growth becomes a real problem. At that point your application must:

- store each state page under its content identifier and return the same bytes; a missing page must fail with an error, never read as empty;
- keep the unbroken journal prefix and the archive-retention roots that each checkpoint needs;
- keep the lookup pages of the resource archive for every archive head that a restore, an exact replay, or a fork can pass through (see [archiving terminal records](/en/architecture/resources-production/#archiving-terminal-records));
- restore the same archive contracts and semantic hashes for every plugin; and
- check reachability from committed roots before deleting cold data.

### Paged checkpoints

A **paged checkpoint** is the content-addressed form of the current-state checkpoint. It is stored as state pages in a `StatePageProvider`, and each new checkpoint adds only the pages that changed. Since 0.13.2, you can write and restore paged checkpoints through the public API:

- **Write.** `Canwu::prepare_paged_checkpoint(source, provider)` captures current state as a `PreparedPagedSimulationCheckpoint`. Its delta leaves out every page the provider already holds; `source` is the earlier checkpoint, if there is one. `store_and_verify` stores the delta. Preparing changes nothing in the run: the state revision, the checkpoint hash, and every journal stay the same.
- **Restore.** `Canwu::from_paged_checkpoint_and_journal(checkpoint, provider, segments)` and `from_paged_checkpoint_and_journal_with_plugins` rebuild the run from the provider and the evidence prefix: the unbroken journal segments from the start of the run up to the checkpoint. Collect them as the run goes with `journal_segment_since`. Each segment must contain at least one new record, so skip any segment whose start equals its end. A restore runs the same validation as loading a snapshot. Only the pages the restore reads must be in the provider, and a missing one fails with `StatePageUnavailable` instead of reading as empty. Of the archived decision history, the restore reads only the pages that hot decision state depends on; other archived history reports `Unresolved` until `decision_history_location_with_provider` looks it up through a `DecisionArchiveProvider` that serves the same pages.
- **Compact mode.** `CompactedCanwu` offers the same calls. Its evidence prefix is the segments you have sealed, in order, followed by what `journal_segment_since` returns from the end of the last one. Skip that final segment when nothing was recorded after the seal. After a compact restore the prefix changes; see [Restart a compact run](#restart-a-compact-run).

The checkpoint carries no evidence records. Its size follows current state rather than the length of the run, apart from compact-mode continuation data such as one archived-segment header per seal, and each delta holds only the pages that changed. Preparing can still read retained evidence, and a restore still validates the whole evidence prefix.

Keep these caveats in mind:

- Keep the earlier checkpoint's pages in the provider. When a run restored from a paged checkpoint prepares a new one, its delta also leaves out the archived decision pages the run never loaded, so its provider must already hold every page of the checkpoint it was restored from. `store_and_verify` checks only the new pages and the root; use `StatePageRetentionLedger::prepare` and `verify` to check a checkpoint's complete page set.
- A compact restore needs the `_with_plugins` form whenever the checkpoint names a plugin.
- A paged root is not a state identity, because it also commits to which evidence is sealed. Any restore from sealed segments, through `Canwu` or `CompactedCanwu`, keeps the original checkpoint hash but gets a different paged root, and a later seal does not bring the old root back. A run that has never sealed evidence restores to the same paged root. Compare checkpoint hashes, not paged roots.

### Restart a compact run

A compact restore, whether from a paged checkpoint or through `CompactedCanwu::from_checkpoint_and_journal` and its `_with_plugins` form, keeps the whole prefix you supplied as retained evidence. That changes which segments later restores need:

1. Until the restored run seals again, a checkpoint of it uses the prefix you restored it from, followed by what `journal_segment_since` returns from that prefix's end.
2. Its next `seal_evidence()` returns one segment that starts at the beginning of the run and replaces every segment sealed before it.
3. From then on, the prefix starts with that new segment, followed by what `journal_segment_since` returns from its end.
4. Keep the earlier segments only for checkpoints taken before that seal.

A prefix that still lists the earlier segments in front of the new one is not contiguous, so restoring from it fails.

The repository's [versioning and persistence contract](https://github.com/PeiyuanQi/canwu/blob/main/docs/versioning.md) lists format numbers, paged-storage contracts, and archive invariants.

## Version and save compatibility

:::note
Canwu 0.15.0 writes snapshot format 8, commitment format 4, checkpoint/evidence-journal format 4, and paged-checkpoint envelope format 4. A save also records the exact `engine_version`, so a 0.15.0 run loads only 0.15.0 saves. A save from 0.14.0 or earlier cannot be loaded, and editing its recorded `engine_version` does not make it load; keep the older engine to read it, or export the data with your own tool.
:::

Canwu 0.15.0 is a minor release. The formats and hash algorithms are unchanged, and the engine saves nothing new: the index that answers [operation-keyed draws](/en/architecture/randomness/#what-a-keyed-draw-costs-later) is rebuilt on restore, and a [boundary profile](/en/architecture/settlement/#profiling-a-boundary) is never saved. What changes for saves and for code:

- **A save that could not be loaded.** Loading now applies the same rule as settlement to the records a knowledge record [supersedes or contradicts](/en/architecture/knowledge-information/#superseding-an-earlier-record). Under 0.14.0, a plugin that superseded a holder's record in two boundaries at one instant wrote a save that no load accepted.
- **Sealed runs behave as their replays do.** An exact retry of an [operation-keyed draw](/en/architecture/randomness/#retries-after-evidence-is-sealed) returns the recorded draw even after `seal_evidence` removed the evidence it cites; 0.14.0 refused it with `InvalidRandomOperationEvidence`. A [fiscal report](/en/architecture/fiscal/#how-a-report-is-published) published after a seal supersedes the report published before it; under 0.14.0 the holder kept two current reports and the sealed run failed exact replay.
- **Code to update.** `PersonDraft` carries an optional `PersonPlacement` in place of its `government` and `current_location` fields, and `BoundaryPersonCreation::person` is a `BoundaryCreatedPerson`. `SocietyPlugin` is no longer a unit struct, so write `SocietyPlugin::DAILY`. `ResourceState::prepare_resource_archive` takes the archive store. `ResourceCompletionOperationV1` and `FiscalAction` gain variants. `SocietyCohortExchangeLedger`, `ResourceArchiveIndexDirectoryV1`, `PreparedResourceArchiveBatchV1`, `ResourceProtectedFloorRequestV1`, `FiscalAuthorityBinding`, `FiscalAuditFinding`, and `FiscalState` gain public fields, so a floor request literal adds `install: None` and an authority binding literal adds `rebound_by: None`. `MAX_RESOURCE_ARCHIVE_LOOKUP_DIRECTORIES` is removed. Read fiscal reports with `fiscal_reports`; one `fiscal_report` record no longer decodes as a whole `FiscalProjection`.
- **Plugin identities.** The semantic hashes of the society, resource, and fiscal plugins change. A society run is restored and replayed only with a plugin registered on the same [settlement cadence](/en/tutorials/cases/local-community-diffusion/#settle-on-another-cadence).
- **Resource archives.** Keep the lookup pages of the resource archive: a restore, an exact replay, or a fork reads the lookup index of every archive head it passes; see [archiving terminal records](/en/architecture/resources-production/#archiving-terminal-records). Archive directories written by 0.14.0 do not decode, but no 0.15.0 run can reach one.
- **Fiscal records are checked on entry.** An invalid fiscal catalog or state is refused when a run is created or restored; under 0.14.0 it failed the first boundary that admitted anything. The fiscal state record now references each observer's person, so build it with `FiscalState::into_record`; a state that names an observer who does not exist is refused. The `fiscal_report` knowledge schema is at version 2, and a scenario whose knowledge carries a version-1 report record is refused.
- **Refusals that no longer stall a run.** Refused society commands and defective society packets are recorded as rejections, and a stale resource archive commit against a full candidate budget no longer fails every later boundary. A tracked resource command that reuses an operation key for a different request is refused or left unsettled. Several fiscal actions settle in one boundary, and one that cannot be given an outcome is dropped with an event.

The engine version in every checkpoint hash changes, as with any version change. First-party plugins that take their plugin version from the crate version report a new one. The exact engine-version check rejects 0.14.0 saves; keep the 0.14.0 engine to read them.

Canwu 0.14.0, the previous minor release, replaced 0.13.3's day read with a read of [any window of simulated time](/en/architecture/settlement/#counting-the-boundaries-of-a-period): `SimulationView::boundaries_between(from, to)` returns `BoundaryWindow`, and the host-side calls are `Canwu::boundaries_between` and `CompactedCanwu::boundaries_between`. A boundary system declares how far back it reads with the new contract field `BoundarySystemContract::boundary_schedule_horizon` (at most `MAX_BOUNDARY_SCHEDULE_HORIZON`, 366 days). `boundaries_on_day` and `DayBoundaries` are removed, so code that used them, or that builds a `BoundarySystemContract` with a struct literal, needs a change. The field is left out of a saved contract when it is zero, so other plugins' descriptors and semantic hashes are unchanged, and the formats and hash algorithms are unchanged too. The engine version in every checkpoint hash changes, as with any version change. First-party plugins that take their plugin version from the crate version report a new one. The exact engine-version check rejects 0.13.3 saves; keep the 0.13.3 engine to read them.

Canwu 0.13.3, the previous patch release, added the first form of this read, which read one day at a time: `SimulationView::boundaries_on_day` behind the new `StateKey::core_boundary_schedule` read; the host-side calls `Canwu::boundaries_on_day` and `CompactedCanwu::boundaries_on_day`; the types `DayBoundaries`, `BoundarySummary`, `BoundaryIngressCount`, `BoundaryIngressKind`, and `BoundaryIngressOrigin`; and `SimTime::day` with `SimTime::MINUTES_PER_DAY`. The engine rebuilds the day's settled boundaries from the journals on restore, so saves gain no field. Every change is additive, so existing code still compiles, and the formats, public type shapes, and hash algorithms are unchanged. The engine version in every checkpoint hash changes, as with any version change. First-party plugins that take their plugin version from the crate version report a new one. The exact engine-version check rejects 0.13.2 saves; keep the 0.13.2 engine to read them.

Canwu 0.13.2 is a patch release. It adds public API calls that write and restore [paged checkpoints](#paged-checkpoints), which the engine already implemented internally: `Canwu::prepare_paged_checkpoint`, `Canwu::from_paged_checkpoint_and_journal`, and `Canwu::from_paged_checkpoint_and_journal_with_plugins`, plus the same three calls and `journal_segment_since` on `CompactedCanwu`. Every change is additive, so existing code still compiles. The formats, public type shapes, and hash algorithms are unchanged. Each checkpoint hash includes the engine version, so every run's checkpoint hashes, and the paged roots that record them, differ from 0.13.1, as they do across any version change. First-party plugins that take their plugin version from the crate version report a new one. The exact engine-version check rejects 0.13.1 saves; keep the 0.13.1 engine to read them.

Canwu 0.13.1, the previous patch release, kept the 0.13.0 formats and existing public types and added three public items: `SimulationView::replay_stable_domain_record_version`, `canwu_military::MILITARY_REJECTION_EVENT`, and `OperationState::validate`. Its checkpoint hashes all differ from 0.13.0, and 0.13.0 saves do not load. The semantic hashes of the production, historical research, fiscal, military, and resource plugins also changed, as did those of the `canwu-economy-reference` plugin, its typed-evidence adapter, and the `canwu-force-supply-reference` plugin.

It fixed [deferred decision tickets](/en/architecture/decisions/) that never expired in a live run: such a ticket stayed open past its deadline, yet every later request on it was rejected as `ClosedTicket`. It now expires at the first boundary after its deadline, as it already did in a run restored from a snapshot.

It also fixed evidence checks that could reject a command in a run sealed with `seal_evidence` yet accept it in the exact replay of that run. [Production](/en/developer/production-economy/) executions, facility projects, and realized output, [access grants](/en/developer/production-economy/#delegated-access-grants), fiscal commutation quotes and [execution receipts](/en/architecture/fiscal/), and the record versions a historical research assessment names must now be versions that a seal cannot change, normally the current version of each record. Generic research citations, such as events and boundaries, are still checked against retained evidence, so a sealed run can still reject an assessment that its exact replay accepts. Finally, bad [military](/en/architecture/military/) and fiscal commands no longer make every later boundary fail; they are recorded as rejected.

- Pin an exact release or Git revision for any application that keeps saves.
- Treat a plugin semantic-hash change as a behavior change. Any release, even a patch release such as 0.13.0 → 0.13.1, can change the semantic hashes of several extensions at once, and older saves that use those extensions then fail to load.
- Canwu does not migrate old saves. To carry history across an engine upgrade, run your own export and import, or keep the engine that wrote the data.
- New releases add enum variants and struct fields, so exhaustive `match` statements and struct literals may need updates.

For what each release changed, see the [versioning and persistence contract](https://github.com/PeiyuanQi/canwu/blob/main/docs/versioning.md).

## Production checklist

- Pin the engine version and plugin semantic environment.
- Do one full save, process restart, and load, then compare checkpoint hashes.
- Run one exact replay and compare the final checkpoint hash.
- Simulate an outbox timeout and confirm that retrying by `delivery_id` does not repeat the outside effect.
- Write down what an upgrade does with old saves: export and re-import them, keep the old engine to read them, or drop them.
