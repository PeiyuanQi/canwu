Canwu is a headless historical simulation engine. The host owns windows, maps, networking, input, AI scheduling, and the frame loop.
Canwu owns generic authoritative state, validation, deterministic time, events, and evidence; concrete world models and commands belong to the domain integration selected by the application.

## Add dependencies

The current `main` branch requires Rust 1.88 or newer. The following dependencies are appropriate for evaluating the current development version:

```toml
[dependencies]
canwu-api = { git = "https://github.com/PeiyuanQi/canwu", branch = "main" }
canwu-reference-world = { git = "https://github.com/PeiyuanQi/canwu", branch = "main" }
```

`canwu-reference-world` is a replaceable starter integration, not an engine foundation crate. The old `canwu-world` crate is retired. Do not depend on `canwu-sim` or another runtime implementation crate.

Before production, pin an exact published release or Git revision and pair every engine upgrade with an explicit save migration.

## Minimal host flow

```rust
use canwu_api::{Canwu, CommandRequest, CommandRequestId, EntityRef, Issuer, SimDuration};
use canwu_reference_world::{
    MovementCommand, ReferenceWorldPlugin, demo_scenario, order_movement,
    snapshot as reference_snapshot,
};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let (scenario, ids) = demo_scenario()?;
    let plugin = ReferenceWorldPlugin;
    let mut canwu = Canwu::new_with_plugins(35, scenario, &[&plugin])?;

    let command = order_movement(
        Issuer::Actor(ids.commander),
        &MovementCommand {
            subject: EntityRef::Army(ids.army),
            destination: ids.eastern_territory,
            cargo: Vec::new(),
        },
    )?
    .at_time(canwu.time());
    canwu.enqueue_command(
        canwu.time(),
        0,
        CommandRequest::new(CommandRequestId::new(1), canwu.revision(), command),
    )?;
    canwu.advance_canonical(SimDuration::hours(19))?;

    println!(
        "army_location={}",
        reference_snapshot(&canwu)?
            .army(ids.army)
            .expect("demo army exists")
            .location
    );
    Ok(())
}
```

Run the complete example from the repository root:

```shell
cargo run -p canwu-reference-world --example starter
```

The value `35` is a deterministic demo seed, `0` is the command priority, and the 19-hour advance crosses the reference movement system's settlement time.
The program prints the army's final location; the complete `starter` example also verifies saving, forking, and exact replay.
Production applications normally construct their own `Scenario` and plugins. The reference integration's `demo_scenario()` is only a runnable template.

## Choose an ingress path

| Entry point | Use it when |
| --- | --- |
| `submit(CommandEnvelope)` | The host already owns a typed domain command and issuer identity |
| `process_command(CommandRequest)` | An external service needs request identity, revision validation, and recorded outcomes |
| `enqueue_command(...)` | A command must enter at an explicit simulation time and priority |

The domain integration translates UI or agent intent into a typed domain command. Every ingress path preserves the same rule: the host never receives a mutable world reference.

## Withdraw queued plugin input

Plugin input queued with `enqueue_plugin_ingress` can be withdrawn while it is still queued and strictly before its due time:

```rust
let queued = canwu.enqueue_plugin_ingress(request)?;
// The player withdraws the order before it is due.
canwu.cancel_plugin_ingress(queued.ingress_id, "withdrawn by player")?;
```

Only the issuer may withdraw an item. The host withdraws public packets it enqueued with `cancel_plugin_ingress`. Internal packet types need `cancel_permitted_plugin_ingress` with the owning plugin's registration permit, which also covers items that plugin scheduled itself. A plugin's boundary system withdraws items its plugin scheduled with `BoundaryDirective::CancelPluginIngress`. The withdrawal is journaled as its own `IngressPayload::PluginCancellation` record naming the item, the `IngressCancellationAuthority`, and a reason of at most 1,024 bytes. The withdrawn item is never admitted and nothing is rolled back. Items that are already due, admitted, archived, or withdrawn fail with `LateIngress`; another issuer's item fails with `InvalidAuthority`; an unknown ID fails with `EvidenceUnavailable`. Snapshots, checkpoint journals, and exact replay keep the withdrawal.

## People who can no longer act

Since 0.12.0 the runtime keeps each person's availability (`PersonAvailability`): a life state (`Alive`, `Dead`, `Missing`) and a custody state (`Free`, `Detained`, `Hostage`, `Captive`, `Hiding`, `Exile`). Your application decides when a person dies, is captured, or is released, and records it from a phase-7 or phase-10 boundary system that declares `StateKey::core_person_availability()` and returns `BoundaryDirective::SetPersonAvailability`. Read it with `canwu.person_availability(person)`; `None` means alive and free.

A person who is not alive, or who is detained or captive, is unavailable:

- command admission rejects a command whose issuer, decision actor, or responsible institutional actor is unavailable with `IssuerUnavailable`, recorded as a persisted rejection for tracked requests;
- a decision ticket cannot be opened, prepared, or resolved while its person decision maker (`DecisionMakerUnavailable`) or its controller's authority person (`IssuerUnavailable`) is unavailable;
- at the end of the boundary that makes the person unavailable, open tickets where they are the decision maker are cancelled with `decision_maker_unavailable`, and open tickets whose controller acts for them are cancelled with `controller_authority_unavailable`.

Hostage, hiding, and exile stay admissible by default; add stricter rules in your own systems. A cancelled ticket is not reassigned. When only the controller's authority person became unavailable, continue the decision by opening a new ticket for an available controller with `parent_ticket` set to the cancelled one. No new ticket can be opened for a decision maker who is still unavailable.

Since 0.13.0, a successor can also continue the decision of a decision maker who died or was captured. Open the new ticket with the successor as decision maker, assigned to a controller bound to the same non-empty `seat_id` as the cancelled ticket's controller, and set `parent_ticket` to the cancelled ticket. This seat succession keeps the lineage on the new ticket's trace; a parent of a different decision maker in a different seat is still rejected.

## Limit rule explanations

Boundary systems may record [evaluation traces](/en/architecture/settlement/#evaluation-traces) to explain rule results. The run configuration bounds them for all systems together: by default 4,096 traces per boundary and 32 terms per trace, at most 65,536 and 256. Declare other bounds before the run starts with `RunConfiguration::with_evaluation_limits(EvaluationLimitsV1 { traces_per_boundary, terms_per_trace })`; a trace limit of zero forbids traces. A boundary whose systems exceed a bound fails with `EvaluationTraceLimitExceeded` and commits nothing, so size the limits for all systems and seats in one boundary together, not per seat. Traces also count toward journal size.

## Drive time

<Steps>
1. The host reads wall time, turn input, or research workflow progress.
2. The host converts that input into `SimDuration` according to its own speed policy.
3. Event-driven hosts call `advance()`; hosts with daily, turn, or other boundary systems call `advance_canonical()` or explicit `settle_boundary()`.
4. The host refreshes presentation from events, boundary receipts, or a read-only projection produced by its domain integration.
</Steps>

Do not feed floating-point frame deltas directly into authoritative state. See the [continuous-time game loop tutorial](/en/tutorials/continuous-game-loop/) for the complete pattern.
