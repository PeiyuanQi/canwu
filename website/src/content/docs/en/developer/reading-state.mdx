Canwu separates generic authoritative state from actor knowledge, while a domain integration builds concrete world projections. The most important read decision is what the caller is allowed to know.

## Choose by caller

| Caller | Preferred interface | Purpose |
| --- | --- | --- |
| Trusted server, debugger, or test | `entities()`, `domain_records()`, `events()`, `boundaries()`, `person_availabilities()`, `pending_transition_manifests()` | Read generic authoritative state and complete evidence |
| Domain rule or renderer adapter | Integration `snapshot()` or equivalent projection | Assemble typed domain records into a detached view |
| Player or in-world agent | `viewer_for_actor()` + `query_knowledge()` or `evaluation_traces()` | Read only that actor's knowledge, and the rule explanations it may see, without leaking ground truth |
| Explanation UI | `explain()` | Build causal explanations from recorded events or failures |

## Two read paths (excerpt)

This excerpt shows the separation between a trusted projection and actor knowledge; it is not a standalone program.

```rust
use canwu_api::{Canwu, KnowledgeQuery};
use canwu_reference_world::{ReferenceWorldPlugin, demo_scenario, snapshot};

let (scenario, ids) = demo_scenario()?;
let plugin = ReferenceWorldPlugin;
let canwu = Canwu::new_with_plugins(35, scenario, &[&plugin])?;

let server_world = snapshot(&canwu)?;
let commander_knowledge = canwu
    .viewer_for_actor(ids.commander)?
    .query_knowledge(&KnowledgeQuery::default())?;
```

The reference integration's `snapshot()` is a trusted projection containing full world truth. Do not send it unchanged to players, actor agents, or untrusted clients.

The reference world is only one integration. A custom domain assembles its own projection from `typed_domain_record()` while using `CanwuViewer` for actor knowledge.

## Build a client-safe payload

The host should copy only the fields its UI needs from `commander_knowledge` into a host-defined DTO, then serialize that DTO. For example:

```json
{
  "actor": "commander",
  "knowledge_items": [
    { "summary": "Road east is passable", "confidence": "reported" }
  ]
}
```

The host owns this shape. It may contain only information returned by the actor-knowledge query; do not merge in `server_world`, hidden entities, or debugger-only fields.

## Plan from a holder's knowledge

Route planning for a person or institution should use only what that holder knows. `canwu-correspondence` builds such a holder planning snapshot with the same rule its own plugin uses:

```rust
use canwu_correspondence::planning_snapshot_from_holder_knowledge;

let (snapshot, read_set) =
    planning_snapshot_from_holder_knowledge(view, &holder, observed_at)?;
let plan = plan_route(&snapshot, &request)?;
```

Call it inside a plugin system or command handler that declares the `canwu.core.knowledge` read. It admits only the endpoints and connections that the holder's ledger asserts at the read cut the view derives, and it fails if a known connection names an endpoint the holder does not know. The snapshot's `knowledge_cut` records that cut. The returned `KnowledgeReadCutDigest` is evidence of which facts were read, and it stays the same while those facts are unchanged. The view read itself is system access, so take `holder` from admitted authority, such as the command issuer, never from an unvalidated payload.

Outside the runtime, pass a query result you already hold, such as a restricted viewer's `query_knowledge(&planning_knowledge_query())`, to the pure `planning_snapshot_from_knowledge_result`. A paginated result is rejected because a partial page cannot prove the holder's whole network.

## Explain a rule result

When a boundary system records an [evaluation trace](/en/architecture/settlement/#evaluation-traces), a player or agent can see how a rule arrived at a number without seeing the evidence behind it:

```rust
let viewer = canwu.viewer_for_actor(ids.commander)?;
for trace in viewer.evaluation_traces(&EntityRef::Army(ids.army), None)? {
    println!("{} {} = {}", trace.rule_id, trace.rule_version, trace.result);
    for term in &trace.terms {
        println!("  {}: {}", term.term_id, term.contribution);
    }
}
```

`evaluation_traces(subject, after)` returns `EvaluationTraceView` values from the boundaries after `after`, or from every retained boundary for `None`, in boundary and recording order. A view keeps the rule, subject, boundary, result, and each term's contribution; it omits evidence and the producing plugin and system. A person or institution sees traces about its own entity, and traces about another subject only when a knowledge publication naming that subject reached its ledger before the trace was evaluated, so a holder never gains the breakdown of a subject it had not yet learned of. Research and developer principals see every trace, and a public principal receives `InvalidKnowledgeAuthority`. The trusted `boundaries()` read keeps the full records with their evidence.

## Follow multi-owner transitions

Only trusted host reads expose transition manifests. `pending_transition_manifests()` lists the registered manifests whose ready boundary has not settled, and each boundary's `BoundaryReceipt::transition_audits` and `BoundaryRecord::transition_audits` record the manifests that settled there as `Committed` or `Expired`. Inside the simulation, only a manifest's coordinator and participants read it, through `SimulationView::transition_manifests` and `transition_audits` after declaring the `canwu.core.transitions` read. Present a transition to players from the application's own records or reports, not from the audit.

## Presentation copies state; it does not write back

A renderer may copy locations, routes, and statuses from a domain projection, then keep its own animation and interpolation data. Presentation state never feeds back into Canwu. Continuous clients keep wall time, simulation time, and presentation time separate.
