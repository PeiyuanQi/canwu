Canwu separates generic authoritative state from actor knowledge, while a domain integration builds concrete world projections. The most important read decision is what the caller is allowed to know.

## Choose by caller

| Caller | Preferred interface | Purpose |
| --- | --- | --- |
| Trusted server, debugger, or test | `entities()`, `domain_records()`, `events()`, `boundaries()` | Read generic authoritative state and complete evidence |
| Domain rule or renderer adapter | Integration `snapshot()` or equivalent projection | Assemble typed domain records into a detached view |
| Player or in-world agent | `viewer_for_actor()` + `query_knowledge()` | Read only that actor's knowledge without leaking ground truth |
| Explanation UI | `explain()` | Build causal explanations from recorded events or failures |

## A domain projection is not a player view

```rust
use canwu_api::{Canwu, KnowledgeQuery};
use canwu_reference_world::{ReferenceWorldPlugin, demo_scenario, snapshot};

let (scenario, ids) = demo_scenario()?;
let plugin = ReferenceWorldPlugin;
let canwu = Canwu::new_with_plugins(35, scenario, &[&plugin])?;

let server_world = snapshot(&canwu)?;
let commander_knowledge = canwu
    .viewer_for_actor(ids.commander)?
    .query_knowledge(&KnowledgeQuery::default())?;
# Ok::<(), canwu_api::CanwuError>(())
```

The reference integration's `snapshot()` is a trusted projection containing full world truth. Do not send it unchanged to players, actor agents, or untrusted clients.

The reference world is only one integration. A custom domain assembles its own projection from `typed_domain_record()` while using `CanwuViewer` for actor knowledge.

## Presentation copies state; it does not write back

A renderer may copy locations, routes, and statuses from a domain projection, then keep its own animation and interpolation data. Presentation state never feeds back into Canwu. Continuous clients keep wall time, simulation time, and presentation time separate.
