Canwu keeps the simulation core domain-neutral. Host applications add military, economic, political, or social rules through
simulation plugins, domain schemas, command handlers, and boundary systems rather than mutating the live world.

## Choose an extension path

| Need | Use |
| --- | --- |
| A user action or service request produces a local change | Register a domain command with `register_command()` |
| Several systems coordinate at the same day, turn, or time point | Register a boundary system with `register_boundary_system()` |
| The plugin owns typed domain data | Register domain schemas and use the domain-record APIs |
| Results require stable randomness | Declare plugin random streams so each draw enters evidence |

## Minimal simulation-plugin structure (excerpt)

This excerpt shows the registration shape only. The runnable example contains the payload schema, handler, and complete imports.

```rust
struct StancePlugin;

impl SimulationPlugin for StancePlugin {
    fn name(&self) -> &'static str { "example-stance" }
    fn version(&self) -> &'static str { "1.0.0" }
    fn semantic_hash(&self) -> &'static str { "a33fb7c59ae5a17685bd94f99154c5423dc7bf70d3dbde6ef4daf73670a37d26" }

    fn register(&self, registrar: &mut PluginRegistrar<'_>) -> Result<(), CanwuError> {
        registrar.register_command(stance_descriptor(), set_stance)
    }
}
```

`stance_descriptor()` declares the payload shape and read/write `StateKey` values. `set_stance()` queries through the read-only
`SimulationView`, checks the issuer with `CommandContext`, and returns `SystemDirective` values describing the change.
It never receives a mutable world reference.

Run the complete example:

```shell
cargo run -p canwu-api --example plugin
```

When the army commander submits `set_stance`, Canwu validates the payload and authority before committing the stance component.
An unauthorized issuer receives `InvalidAuthority`, and no partial state change is committed.

## When to use a boundary system

Use a boundary system when supply, demand, resource allocation, and consequences must coordinate in one transaction.
Its contract should declare:

- settlement phase and cadence;
- reads, writes, and same-boundary visibility;
- resource offers, reservation requests, and allocation dependencies;
- domain events it may emit; and
- required random streams and domain schemas.

Canwu runs systems in fixed phase order, validates declared access, performs deterministic allocation, and commits the result atomically.
See [phased boundary and allocation](/en/tutorials/phased-boundary/) for a complete example.

## From a requirement to a replayable extension

1. Choose a stable plugin name, version, and semantic hash.
2. Register the domain schemas, commands, and boundary systems owned by the plugin.
3. Let handlers read only through `SimulationView` and return declared changes.
4. Submit domain commands or canonical ingress through public entry points; do not retain a live runtime reference.
5. Verify save/load, exact replay, authority failure, and atomic rollback.

Before selecting an extension, confirm its public version, dependency graph, and persistence contract.
Historical content, scenario parameters, and host rules remain owned by content packs or the host application.

## Lifecycle rules

- Register plugins before commands, scenario validation, or loads that depend on them.
- Provide the same plugin set and semantic hashes when restoring a save or replaying a journal.
- Do not retain live runtime references or bypass canonical ingress to mutate state.
- Treat a semantic-hash change as an executable-behavior change that requires migration or a new version.
- Consume extension contracts through `canwu-api` from application code.

Before implementation, review the [five architectural boundaries](/en/architecture/#five-architectural-boundaries), then start from the public example closest to your use case.
